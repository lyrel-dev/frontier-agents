01 · Executive view

Standardize the work—not the privileges.

Treat each agent as a separately authorized worker. Connect useful outputs through reviewed evidence, existing repositories, and owned work items.

This companion consolidates recurring architectural concerns from the four prior reports. It focuses on everyday work, not a speculative autonomous platform. AWS lists DevOps Agent, Kiro, Security Agent, and FinOps Agent in the frontier-agent portfolio. [X01]

What this is—and is not. The common architecture is an author-proposed operating design. It does not assert a shared AWS backend, universal agent API, shared cross-product memory, or one approval policy. Documented mechanisms, feature limitations, and team recommendations are identified separately.

Keep the first deployment small

Start with one workload, one named owner, and one bounded task. Establish evidence quality and the native control path before adding recurrence or cross-agent handoffs.

Preserve the existing control points

Use normal code review, deployment approval, authorized testing, and source-data reconciliation. A generated recommendation or a completed run is not an authorization to act.

Standalone HTML: no external scripts, fonts, analytics, or server. Source links open official websites. Browser controls do not change AWS resources.

02 · Logical reference architecture

Separate context, work, authority, and evidence.

The stages below describe the team’s operating process, not the agents’ internal implementation. Permissions apply at every stage; a required action gate must be satisfied before its effect occurs. Later merge and deployment decisions remain separate.

05 · Daily composition patterns

Four useful handoffs before building an orchestrator.

These are proposed team workflows assembled from documented building blocks. None has been run against your environment, and none implies a single native cross-agent transaction.

Operations + development

W01 · Incident → reviewable fix

Baseline without release-preview dependencies

Team-composed workflow using existing incident, repository, and deployment processes; not a native four-agent transaction.

  1. Investigate

    DevOps Agent assembles an evidence-backed account of the scoped incident. The SRE checks timestamps, deployed version, missing telemetry, and competing explanations.

  2. Create the handoff

    The SRE creates a bounded issue or implementation specification with the observed failure, evidence links, affected repository, regression test, and acceptance criteria.

  3. Implement

    Kiro works on the selected repository and proposes a PR/MR. Do not pass production credentials or an instruction to apply every suggested mitigation.

  4. Review and deploy

    A reviewer validates the diff and independent CI results. The existing deployment process authorizes the release; emergency remediation remains a separate native approval path.

  5. Close with evidence

    Record the deployed commit and verify recovery using telemetry. Feed an accepted lesson into the reviewed runbook or prevention backlog.

Done means: Closure requires an accepted change or documented no-change decision plus an observed operational outcome—not merely a completed investigation.

Stop or escalate: Pause on inaccessible evidence, uncertain ownership, unrelated code changes, or a proposed effect outside the authorized task.

Application security + development

W02 · Security finding → verified repair

On-demand pentest baseline; code-review integration is optional preview

Use either configured Security Agent remediation or a separately scoped Kiro coding task. Avoid assigning the same repair to two writers at once.

  1. Authorize and isolate

    The security owner confirms allowed targets, excluded paths, test identity, approved time window, and a recoverable non-production environment.

  2. Triage evidence

    Review the finding’s affected path, reproduction material, confidence, and impact. Establish which exact deployment and code revision were assessed.

  3. Propose the fix

    Choose one remediation owner. Preserve the finding reference and add an explicit regression test; the generated fix is a proposal, not a release authorization.

  4. Review and retest

    Run ordinary code review and regression checks. Deploy the candidate to the authorized test environment and revalidate the known finding.

  5. Document closure

    Attach the revalidation outcome and residual coverage limitations to the issue. A known finding passing revalidation is not a claim of complete application security.

Done means: Closure requires a reviewed repair, the tested deployment identity, and evidence for the original finding’s outcome.

Stop or escalate: Stop testing on unexpected production reach, unsafe side effects, scope drift, or missing recovery capability.

FinOps + platform + development

W03 · Cost anomaly → controlled change

Preview-dependent · FinOps Agent

An analytical recommendation becomes an engineering decision only after source reconciliation and workload review. This is not autonomous resource optimization.

  1. Investigate the anomaly

    FinOps Agent analyzes a supported anomaly or an on-demand cost question. Record affected accounts, time range, dimensions, and cost basis.

  2. Check operational constraints

    The workload owner compares utilization, reliability requirements, and recent changes; DevOps Agent may assist with connected operational context.

  3. Choose an owned action

    Create an issue that separates estimated savings from risks and assumptions. A budget or commitment purchase needs its existing approval route.

  4. Prepare a reviewable change

    For a code or IaC change, give Kiro a narrow task and required validation steps. The normal plan, review, and deployment process remains authoritative.

  5. Measure the result

    After an approved change and a suitable observation window, reconcile actual cost and service health. Record confounding workload changes and avoid claiming all differences as savings.

Done means: Closure requires a verified engineering outcome; savings remain estimates until measured with comparable data.

Stop or escalate: Do not proceed when the cost basis is unclear, an owner is missing, or a proposed saving threatens the service objective.

Recurring work without a shared control plane

W04 · Daily engineering review → owned backlog

Mixed baseline; optional FinOps inputs are preview

Independent runs feed an existing team review. No common scheduler, shared memory, automatic Security Agent schedule, or native digest aggregator is asserted.

  1. Choose one report owner

    Define the review’s audience, inputs, data freshness, and publication destination. Keep sensitive security evidence behind its own access boundary.

  2. Run supported tasks separately

    Use a configured DevOps custom-agent schedule, a narrow Kiro maintenance automation, and—when approved—a FinOps recurring report. Review current security findings through its documented workflow.

  3. Normalize the handoffs

    Use the shared work-item fields for each accepted item. Keep source run IDs and clearly label stale, missing, or preview-derived information.

  4. Assign or discard

    At the team review, accept specific tasks with accountable owners. Reject duplicate work and track why suggestions were not actionable.

  5. Tune recurrence

    Adjust scope and frequency based on accepted work, review effort, and false or duplicate findings. Disable an automation that cannot sustain a useful signal.

Done means: The output is a small owned backlog and a documented decision trail, not an unreviewed stream of notifications.

Stop or escalate: Suspend publication when destination access, data classification, ownership, or source freshness is no longer approved.

06 · Structured presentation transcript

Present the architecture as an operating decision.

Eight sections with an on-screen message, speaking notes, and a proposed demonstration. These demonstrations are instructions for a future team exercise, not claims that live tests were performed.

01

One operating model, not one implementation

On-screen message: Standardize the work contract and evidence; keep execution and authorization product-specific.
Speaker transcript

We are consolidating the architecture of day-to-day engineering work, not claiming that AWS exposes a single backend for these four products. Our common unit is a bounded work item with an owner, scope, evidence, allowed effects, and acceptance criteria. Each specialist keeps its own access model and execution surface. The practical starting point is an existing incident or issue record, not a new orchestration platform. We can connect outputs manually first and automate a documented interface only when it adds measurable value. Amazon Q Developer and unrelated Continuum capabilities are outside this companion’s scope.

Proposed demonstration · not executed: Walk through one sample incident record and identify the worker, evidence source, reviewer, and deployment owner. Do not run an agent.

02

Make scope and evidence explicit

On-screen message: The task boundary must be enforced and the source data must be reproducible.
Speaker transcript

Before asking an agent to investigate, define the relevant repositories, accounts, application endpoints, and observation period. Give the evidence a version or timestamp and identify its owner. 03

Classify the effect before choosing the gate

On-screen message: Reading, coding, publishing, testing, and mutating infrastructure need different controls.
Speaker transcript

The same word—autonomous—can describe very different effects. A cost query, a Slack post, a branch update, a penetration test, and a production configuration change do not have the same risk or approval semantics. Use the control matrix to identify the exact path, not just the product name. Record whether approval happens per action, at automation setup, or in the repository workflow. An approved handoff is permission to review the next task, not a credential or a reusable production authorization. Test both the allowed and denied paths before expanding scope.

04

Protect the target, not only the worker

On-screen message: A sandbox can still reach a real system; active testing can change real data.
Speaker transcript

Review the full reach of the task: network destinations, test credentials, callback URLs, source repositories, and output channels. Protecting the execution environment alone is not sufficient when its permitted connections reach sensitive systems. Use disposable data and narrowly scoped credentials, and disable live business side effects in a representative test deployment. Decide who stops the run and who restores the environment. Treat a secret placed in a worker as accessible to that work; do not use sandbox isolation as a reason to distribute production credentials broadly.

05

Connect specialists through reviewable artifacts

On-screen message: The shared interface is evidence plus acceptance criteria—not shared credentials or memory.
Speaker transcript

A useful handoff names the finding, the affected version, the proposed change, and how someone will prove that the work is complete. Use documented adapters for calls that genuinely need automation; otherwise, a linked issue and pull request are sufficient for a first pass. 06

Treat every long-running task as a job

On-screen message: Track state, concurrency, partial results, cost, and stop responsibility.
Speaker transcript

A task should have an observable lifecycle and a clear terminal condition. Define retry limits and duplicate handling before connecting event sources, then record what happened when a job failed, timed out, or needed input. A client stopping its wait is not enough evidence that all server-side work has ended. Test the actual cancellation path in a safe environment and reconcile the resulting state. Keep budget and coverage separate: reaching a work limit may leave useful partial findings, but it does not establish complete assessment. Review recurring automation as a standing operational permission, not a one-time chat decision.

07

Verify outcomes and preserve lineage

On-screen message: A completed run is an output; an accepted outcome requires independent evidence.
Speaker transcript

Choose acceptance checks before the work starts. For code, use the intended behavior, the exact candidate revision, and normal review. For an incident, verify the operational recovery. For a security finding, confirm the specific repair and record what was not assessed. For cost work, reconcile the data definition and measure the result after the authorized change. Preserve links between request, run, evidence, approval, change, and outcome. Do not flatten every record into a chat transcript or assume one audit system covers the entire portfolio.

08

Roll out through explicit architecture gates

On-screen message: Start with one bounded workflow, then expand only when evidence justifies it.
Speaker transcript

The proposed rollout begins with an access and data-flow review, then one on-demand workflow, then independent verification, and only then recurring or cross-agent automation. 07 · Adoption and acceptance

Use evidence to decide when to expand.

The checklist is a local self-assessment for your team. Marking a box does not execute a test, enforce a policy, establish compliance, or change an account. Values last only while this page is open unless you export them.

Proposed 30-day rollout

Days 1–3

Inventory and boundaries

Select one workload. Complete identity, context, and data-location review; choose one low-impact on-demand task.

Days 4–7

Prove a single path

Run the agreed safe pilot in your environment. Reproduce evidence and test a harmless denied path before adding integrations.

Days 8–14

Add a handoff

Use one reviewed issue-to-PR or finding-to-fix packet. Record rework, missing context, and reviewer effort.

Days 15–21

Bound recurrence

Add one supported schedule or event path. Test duplicate handling, destination restrictions, and server-side stop behavior.

Days 22–30

Decide with evidence

Review accepted outcomes, error/duplicate rates, reviewer time, run cost, and control exceptions. Expand, narrow, or stop deliberately.

Measure accepted outcomes, not generated volume.

Recommended measures: accepted work items divided by reviewed items; reviewer and rework time; source-evidence completeness; incorrect or duplicate outputs; scope and destination violations; run cost; and verified operational or cost outcomes. Establish a baseline before interpreting improvement. No result or benefit has been measured in this report.
