Use cases/Reliability improvement

AWS DevOps Agent

Prioritize incident-prevention work

Turn evidence-backed improvement proposals into owned engineering work.

Responsible actor. Reliability owner

1. Purpose and scope

The reliability owner has identified recurring themes and needs a manageable prevention backlog. Run or inspect the documented prevention evaluation, then review each recommendation against the incidents it addresses. Separate observability improvements, infrastructure changes, governance work, and code changes because they have different owners and acceptance evidence.

Keep an accepted recommendation linked to its source evidence and normal change process. A recommendation’s priority or estimated effect is not proof that the change has been implemented. During the next operational review, inspect actual progress and post-change observations. This closes the team’s improvement loop without claiming autonomous implementation or measured benefit before either exists.

Inputs
Multiple incident investigations, team priorities and recommendation evaluation.
Expected output
Ranked recommendations with source incidents, expected effect and backlog state.
Execution pattern
Weekly or on demand
Delivery mode
Built-in function

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Inspect the prevention evaluation

    Identify proposals relevant to recurring weaknesses.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Cross-investigation prevention evaluation. Analyze recurring weaknesses and produce improvement proposals.

    Configuration. Incident-prevention evaluations

    Effect. Recommendation

    Verification. Trace a proposed theme or improvement to supporting investigations.

    Failure handling. Keep unsupported patterns as hypotheses and separate proposals from implemented changes.

  2. Prioritize and assign accepted work

    Compare risk, dependencies and implementation effort through normal team review.

    Responsible actor. Responsible engineer or reviewer

    Dependency. Required. Applies to the selected implementation.

    Implementation. Engineering procedure; no native service operation is asserted for this step.

    Effect. Team decision; no implicit service action

    Verification. Record the decision with the source identifiers and evidence needed for the case completion criteria.

    Failure handling. Keep the result unresolved and assign the missing decision or evidence to an owner.

Setup procedure

  1. Verify operator access independently from resource and tool access.
  2. For incident work, start from a signal or scoped manual investigation. For prevention work, inspect a manual or scheduled evaluation over existing investigation evidence.
  3. Inspect triage, current evidence and any observable historical-context retrieval separately.

Proposed checks

  • Current observations contradict a prior cause: the conclusion must follow current evidence.
  • A missing source produces an explicit evidence gap.
  • Correcting routing changes linkage, not production resource state.

Stop behavior. Use supported investigation controls. Steering and feedback do not grant mutation authority.

Supporting procedures for this configuration

This recipe is reused by multiple workflows. The required, optional, or conditional dependencies for this use case are specified in its workflow above.

  • Evidence retrieval through selected tools
  • Incident routing
  • Investigation and operator steering
  • Selective incident-context retrieval
  • Corrective investigation feedback
  • Cross-investigation prevention evaluation

4. Verification and limits

Completion criteria

  • Accepted proposals retain source incidents.
  • An owner and acceptance criterion are assigned.
  • Proposal status is distinct from implementation evidence.

Prerequisites and availability

GA production operations

Limitations

Recommendations are not automatically implemented and may age out when not kept or implemented.

Example request

Run a prevention evaluation and return the highest-priority recommendations with affected incidents and owners.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
