AWS DevOps Agent

Investigate a service incident

Establish an explanation supported by current incident evidence.

Responsible actor. Incident investigator

1. Purpose and scope

A service owner sees elevated errors after a deployment. The investigation begins with the affected service, incident time, and symptoms, not with an assumed deployment defect. Connect the available logs, metrics, traces, repository context, and deployment records, then inspect how the investigation relates the observations across those sources.

The useful result identifies the measurements that support each explanation and the sources that could not be read. A deployment timestamp may provide a lead, but its proximity to the error increase is not sufficient proof of cause. When evidence conflicts, preserve the competing explanations and supply the missing observation through investigation steering rather than turning a plausible summary into a confirmed diagnosis.

Inputs
Incident signal, service scope, UTC window, connected telemetry and deployment context.
Expected output
Investigation record with observations, hypotheses, root-cause versions and evidence.
Execution pattern
Event-driven or on demand
Delivery mode
Built-in function

Variants

New incident

Current evidence is sufficient to begin; prior history is not required.

Missing history never excuses missing current telemetry.

Recurring alarm

Read relevant monitor context and compare it with new observations.

Record knowledge existence, observed retrieval and diagnosis correctness separately.

Operator steering

Supply contrary evidence within the active investigation.

Steering does not authorize a production mutation.

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Read current observations

    Establish the present symptom and affected scope.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Evidence retrieval through selected tools. Invoke the authorized source with the intended identity, resource and observation period.

    Configuration. Provider registration and selected tools

    Effect. Source read

    Verification. Compare returned identifiers and a material measurement with the original source.

    Failure handling. Report the failed read and withhold conclusions that require that source.

  2. Compare historical context

    Treat prior causes as hypotheses, not predetermined answers.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Optional. Relevant historical context is available.

    Platform process. Selective incident-context retrieval. Select a relevant store, inspect its entries and read the content needed by the current task.

    Configuration. Memory stores and entries

    Effect. Context read

    Verification. Distinguish entry existence, observable retrieval and correctness against current evidence.

    Failure handling. Continue without history when current evidence suffices. Do not infer retrieval merely from answer wording.

  3. Investigate and reconsider hypotheses

    Use current evidence and relevant operator steering.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Investigation and operator steering. Read observations, examine hypotheses and accept relevant operator steering in the investigation context.

    Configuration. Incident triage and investigations · Provider registration and selected tools

    Effect. Investigation record

    Verification. Check conclusions against current observations and identify missing evidence.

    Failure handling. Retain competing hypotheses or an inconclusive result instead of inventing certainty.

  4. Record a verified correction

    Preserve the actual cause when a completed diagnosis was wrong.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Conditional. A completed investigation requires verified correction.

    Platform process. Corrective investigation feedback. Record the actual cause separately from routine synthesis of incident history.

    Configuration. Incident triage and investigations · Memory stores and entries

    Effect. Retained correction

    Verification. Inspect saved feedback and any exposed corrective entry.

    Failure handling. Keep the verified correction in the incident system when downstream use cannot be observed.

3. Configuration

Use the applicable configuration below for the selected workflow. Parameters and checks are engineering guidance, not deployable AWS payloads. Product procedures remain in the linked guide sections.

Agent SpaceAuthorized space and account scopeApproved staging space
Incident subjectService identity and actual UTC observation intervalCheckout service and supplied incident window
Historical contextRelevant active monitor or service contextOptional; never a substitute for current evidence

Setup procedure

  1. Verify operator access independently from resource and tool access.
  2. For incident work, start from a signal or scoped manual investigation. For prevention work, inspect a manual or scheduled evaluation over existing investigation evidence.
  3. Inspect triage, current evidence and any observable historical-context retrieval separately.

Proposed checks

  • Current observations contradict a prior cause: the conclusion must follow current evidence.
  • A missing source produces an explicit evidence gap.
  • Correcting routing changes linkage, not production resource state.

Stop behavior. Use supported investigation controls. Steering and feedback do not grant mutation authority.

Cross-tool evidence reconciliation

ParameterConfiguration decisionExample or constraint
Identity mappingService, resource and revision relationships across toolsReviewed application-to-deployment mapping
Observation windowCommon UTC periodExplicit incident interval

Setup procedure

  1. Read source identifiers instead of matching only titles.
  2. Join observations using reviewed service and revision mappings.
  3. Retain unmatched records and contradictory evidence.

Proposed checks

  • Similar timestamps alone do not establish causality.
  • An observation for the wrong account or revision is rejected.

Stop behavior. Continue only with supported relationships and assign gaps to an owner. This is a team procedure, not a universal native correlation feature.

4. Verification and limits

Completion criteria

  • Affected service and UTC interval are explicit.
  • Competing explanations and unavailable sources are retained.
  • The conclusion follows current observations or remains inconclusive.

Prerequisites and availability

GA production operations

Limitations

The output remains an investigation result to verify against current source data.

Example request

Investigate the checkout 5xx increase for the stated service and UTC window; separate observations, hypotheses and missing data.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
