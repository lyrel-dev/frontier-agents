AWS Security Agent

Review a proposed application design

Evaluate a current design against applicable security requirements.

Responsible actor. Architect and security reviewer

1. Purpose and scope

A team proposes a new payment-service design before implementation. Submit the current design material and relevant application context for the eligible review, and identify the enabled requirements that govern it. The assessment should expose assumptions about identity, data flows, and trust boundaries that need owner confirmation.

Review the findings with the architect and distinguish missing design evidence from a demonstrated violation. Design review has a one-off lifecycle, with cloning used for a new review; it should not be described as an automatically refreshed continuous model. The result informs design work rather than approving the future implementation.

Inputs
Current design material, application context and enabled requirement packs.
Expected output
Design findings and reviewed assumptions.
Execution pattern
On demand
Delivery mode
Preview assessment

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Select current design evidence

    Identify the intended system and design revision.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Application-context assembly. Read the connected source and documentation relevant to the selected assessment.

    Configuration. Application sources and integrations

    Effect. Source read

    Verification. Compare source revision and system boundary with the intended subject.

    Failure handling. Exclude mismatched context and document the resulting assessment limitation.

  2. Apply reviewed criteria

    Evaluate the requirements applicable to the design.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Requirement applicability and evaluation. Evaluate supplied evidence against applicable requirements.

    Configuration. Security requirement packs

    Effect. Assessment result

    Verification. Check compliant, violating and inapplicable examples.

    Failure handling. Revise ambiguous applicability; do not treat a pack as a compliance certificate.

  3. Inspect the point-in-time assessment

    Record findings and unresolved architectural assumptions.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Point-in-time design assessment. Assess the submitted design against relevant criteria.

    Configuration. Design reviews

    Effect. Review result

    Verification. Separate missing evidence from demonstrated violation.

    Failure handling. Use the documented new-review or clone path for changed design material.

3. Configuration

Use the applicable configuration below for the selected workflow. Parameters and checks are engineering guidance, not deployable AWS payloads. Product procedures remain in the linked guide sections.

Write featuresOptional comment, repair proposal or ticketDisabled until provider and audience review

Setup procedure

  1. Choose the actual mode rather than assume a shared configuration schema.
  2. Connect matching evidence and enable the intended review criteria.
  3. Inspect preflight and completed results separately.
  4. Review repair proposals through ordinary tests and deployment before revalidation.

Proposed checks

  • A new source revision cannot silently reuse stale acceptance.
  • A requirement may be inapplicable rather than compliant.
  • Regenerating a pack is reviewed as replacement.

Stop behavior. Retain unfinished findings. Disable optional writes without discarding their source evidence.

4. Verification and limits

Completion criteria

  • Design revision and assumptions are explicit.
  • Missing evidence is separate from a demonstrated violation.
  • Accepted findings have owners.

Prerequisites and availability

Preview

Limitations

Design review uses a different one-off lifecycle from reusable run configurations.

Example request

Review the new payment design against the enabled security requirements and list unsupported assumptions.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
