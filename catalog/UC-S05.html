Use cases/Findings and repair

AWS Security Agent

Triage and prioritize security findings

Give findings an evidence-based disposition and accountable next action.

Responsible actor. Finding owner

1. Purpose and scope

A completed assessment contains findings of different severity and evidential strength. Review each material finding in the context of the affected revision, reachable role, exposed data, and reproduction evidence. Add application-owner context before deciding which finding needs immediate repair and which requires more investigation.

The outcome is a disposition and an accountable next action, not merely a sorted severity list. Findings with incomplete evidence should retain that uncertainty. Link accepted work to the original finding identifier so remediation, deployment, and later verification remain traceable even if the issue title or owner changes.

Inputs
Completed assessment findings and application-owner context.
Expected output
Prioritized finding with owner, disposition and remediation plan.
Execution pattern
On demand
Delivery mode
Native operation

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Review the finding in context

    Evaluate the affected revision, application role and supporting evidence.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Finding evidence inspection. Expose the affected context and supporting reproduction or source evidence for review.

    Configuration. Finding evidence and disposition

    Effect. Finding review record

    Verification. Give the finding a disposition using evidence, impact and application-owner context.

    Failure handling. Preserve uncertainty and obtain missing evidence before closure.

  2. Assign priority and responsibility

    Use application impact and evidence rather than severity alone.

    Responsible actor. Responsible engineer or reviewer

    Dependency. Required. Applies to the selected implementation.

    Implementation. Engineering procedure; no native service operation is asserted for this step.

    Effect. Team decision; no implicit service action

    Verification. Record the decision with the source identifiers and evidence needed for the case completion criteria.

    Failure handling. Keep the result unresolved and assign the missing decision or evidence to an owner.

  3. Publish accepted work to Jira

    Preserve finding linkage in an appropriate project.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Optional. A permitted destination and disclosure scope are configured.

    Platform process. Finding publication to Jira. Publish supported issue or comment content to the configured project.

    Configuration. Jira finding publication

    Effect. External publication

    Verification. Inspect actual project audience and original finding linkage.

    Failure handling. Keep the finding owned locally while resolving publication failure.

3. Configuration

Use the applicable configuration below for the selected workflow. Parameters and checks are engineering guidance, not deployable AWS payloads. Product procedures remain in the linked guide sections.

Source, design and finding-review configuration

ParameterConfiguration decisionExample or constraint
Assessment modeOne supported assessment with its own resource lifecycleCode baseline, code change, design or threat model
Evidence revisionSource or design matching the subjectImmutable revision identifier
CriteriaReviewed applicable requirementsSelected enabled pack
Write featuresOptional comment, repair proposal or ticketDisabled until provider and audience review

Setup procedure

  1. Choose the actual mode rather than assume a shared configuration schema.
  2. Connect matching evidence and enable the intended review criteria.
  3. Inspect preflight and completed results separately.
  4. Review repair proposals through ordinary tests and deployment before revalidation.

Proposed checks

  • A new source revision cannot silently reuse stale acceptance.
  • A requirement may be inapplicable rather than compliant.
  • Regenerating a pack is reviewed as replacement.

Stop behavior. Retain unfinished findings. Disable optional writes without discarding their source evidence.

4. Verification and limits

Completion criteria

  • Impact and evidence are reviewed.
  • Finding identity is preserved.
  • Accepted work has an owner and acceptance test.

Prerequisites and availability

Feature-specific

Limitations

Finding count or severity alone is not an adequate risk decision.

Example request

Prioritize the findings using impact, confidence, affected role and reproduction evidence.
