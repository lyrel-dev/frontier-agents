AWS DevOps Agent

Prepare a mitigation plan

Prepare a proposed change that a reviewer can approve, reject or revise.

Responsible actor. Incident owner

1. Purpose and scope

Once the current evidence supports a likely failure mechanism, the incident owner needs a mitigation that can be reviewed. Ask for the proposed target, exact change, expected effect, risks, rollback, and recovery checks. Compare that proposal with the approved runbook and the evidence already collected, especially where the proposed action would affect another service.

The output is a decision document: it should make it possible to approve, reject, or revise the proposal without guessing its effect. A generated plan remains separate from execution. It can be carried out through the ordinary engineering process, or through an eligible directed-action path after the additional controls described in the next use case have been satisfied.

Inputs
Reviewed incident evidence and a specific operational objective.
Expected output
Mitigation proposal suitable for operator approval or normal runbook execution.
Execution pattern
On demand
Delivery mode
Built-in function

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Review the incident explanation

    Use evidence appropriate to the proposed mitigation.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Investigation and operator steering. Read observations, examine hypotheses and accept relevant operator steering in the investigation context.

    Configuration. Incident triage and investigations · Provider registration and selected tools

    Effect. Investigation record

    Verification. Check conclusions against current observations and identify missing evidence.

    Failure handling. Retain competing hypotheses or an inconclusive result instead of inventing certainty.

  2. Review the proposed mitigation

    Compare target, effect, risk and rollback with the approved procedure.

    Responsible actor. Responsible engineer or reviewer

    Dependency. Required. Applies to the selected implementation.

    Implementation. Engineering procedure; no native service operation is asserted for this step.

    Effect. Team decision; no implicit service action

    Verification. Record the decision with the source identifiers and evidence needed for the case completion criteria.

    Failure handling. Keep the result unresolved and assign the missing decision or evidence to an owner.

Setup procedure

  1. Verify operator access independently from resource and tool access.
  2. For incident work, start from a signal or scoped manual investigation. For prevention work, inspect a manual or scheduled evaluation over existing investigation evidence.
  3. Inspect triage, current evidence and any observable historical-context retrieval separately.

Proposed checks

  • Current observations contradict a prior cause: the conclusion must follow current evidence.
  • A missing source produces an explicit evidence gap.
  • Correcting routing changes linkage, not production resource state.

Stop behavior. Use supported investigation controls. Steering and feedback do not grant mutation authority.

Supporting procedures for this configuration

This recipe is reused by multiple workflows. The required, optional, or conditional dependencies for this use case are specified in its workflow above.

  • Incident routing
  • Investigation and operator steering
  • Selective incident-context retrieval
  • Corrective investigation feedback
  • Cross-investigation prevention evaluation

4. Verification and limits

Completion criteria

  • Target and proposed effect are explicit.
  • Risk, rollback and recovery checks are reviewable.
  • Planning has not been represented as execution.

Prerequisites and availability

GA production operations

Limitations

A proposal is not permission to execute. Unsupported or high-risk actions remain outside the action path.

Example request

Propose the lowest-risk mitigation, including blast radius, rollback and recovery checks.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
