Use cases/Application assessment

AWS Security Agent

Assess a running application for vulnerabilities

Assess the explicitly authorized surface and record findings and coverage gaps.

Responsible actor. Application security engineer

1. Purpose and scope

An application owner authorizes assessment of a deployed release. Establish the target surface, permitted effects, source context and execution limit before starting. Public versus private access and authenticated versus unauthenticated testing are independent configuration choices: they determine which paths can be examined, not four independent operational objectives.

Review the saved configuration and follow the resulting run. Record actual revision, roles reached, exclusions, findings and incomplete areas. A recurring schedule or pipeline may initiate later runs, but cannot preserve credentials or target state that have since changed. Interpret an absence of findings only within the paths actually assessed.

Inputs
Authorized target, actual deployed revision, network scope, test identities where needed, sources and work limits.
Expected output
Assessment run with findings, evidence and coverage record.
Execution pattern
Manual, recurring or supported pipeline path
Delivery mode
Configured application assessment

Variants

Public or private network

Choose the actual target route.

Private reachability does not extend authorized scope.

Unauthenticated or selected roles

Choose the application identities to assess.

Login failure leaves protected paths unassessed.

Manual, recurring or pipeline invocation

Choose a supported trigger.

Each run records its own target revision, identities, limits and coverage.

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Assemble application context

    Select source evidence matching the application and intended revision.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Optional. Source code or documentation is selected to enrich application context.

    Platform process. Application-context assembly. Read the connected source and documentation relevant to the selected assessment.

    Configuration. Application sources and integrations

    Effect. Source read

    Verification. Compare source revision and system boundary with the intended subject.

    Failure handling. Exclude mismatched context and document the resulting assessment limitation.

  2. Configure target access

    Define public or private reachability without widening authority.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Target scope and network access. Apply the configured reachability and target rules to assessment access.

    Configuration. Target and network configuration

    Effect. Target connection

    Verification. Confirm the permitted surface and exclusions in an authorized environment.

    Failure handling. Stop when scope or owner authorization is unresolved.

  3. Authenticate the intended role

    Reach the protected paths required by the profile.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Conditional. The profile includes authenticated paths.

    Platform process. Credential resolution and application login. Obtain the test credential and apply it to the application.

    Configuration. Test credentials and preflight

    Effect. Authentication requests

    Verification. Check the actual application identity and protected route, not only credential retrieval.

    Failure handling. Mark protected paths unassessed when login fails.

  4. Reuse a successful login procedure

    Use documented navigation reuse without assuming it proves coverage.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Optional. A usable retained procedure and its reuse setting are available.

    Platform process. Successful login-procedure reuse. Reuse learned navigation where the setting and current login flow permit it.

    Configuration. Login Optimization

    Effect. Authentication requests

    Verification. Distinguish successful login from observable procedure reuse.

    Failure handling. Retest a changed login flow; failed login is not a clean assessment.

  5. Execute and inspect the run

    Retain actual findings, target state and unassessed areas.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Saved assessment and independent execution. Execute against the current configured target and retain an independent result.

    Configuration. Penetration-test configurations and runs · Finding evidence and disposition

    Effect. Active application assessment

    Verification. Record actual revision, roles, exclusions, limit and incomplete areas.

    Failure handling. Treat incomplete or failed execution as a coverage gap, not a pass.

3. Configuration

Use the applicable configuration below for the selected workflow. Parameters and checks are engineering guidance, not deployable AWS payloads. Product procedures remain in the linked guide sections.

Running-application assessment configuration

ParameterConfiguration decisionExample or constraint
TargetAuthorized application and deployed revisionStaging application / demo-r2
NetworkPublic or private route and explicit exclusionsSeparate attack targets from login support paths
IdentityRepresentative test roles and credential strategyTest customer role; no production credential
Run limitsConfigured work limits and responsible ownerOwner-approved limit, not assumed wall-clock duration

Setup procedure

  1. Review the saved scope before starting execution.
  2. Test target reachability and actual application identity.
  3. Start a separate run and retain excluded or incomplete paths.
  4. For revalidation, confirm the deployed repair and select original findings rather than run broad discovery.

Proposed checks

  • Failed authentication leaves protected paths unassessed.
  • Each run identifies the actual target revision and roles.
  • Revalidation retains the original finding and separate job.

Stop behavior. Stop unexpected effects. Control future schedules separately from current jobs, findings and external tickets.

Setup procedure

  1. Verify eligibility and bind the pipeline to the saved assessment.
  2. Invoke and observe the server-side job, retaining revision and run identity.
  3. Apply the team gate only after interpreting actual scope and coverage.

Proposed checks

  • Invocation failure is not successful assessment.
  • An observation timeout does not imply that the underlying job stopped.
  • A new deployed revision requires matching assessment evidence.

Stop behavior. Stop the actual assessment using supported controls; stopping the pipeline runner is not assumed to cancel it.

4. Verification and limits

Completion criteria

  • Target revision and owner authorization are retained.
  • Reached roles and paths are known.
  • Failures and exclusions remain coverage limitations.

Prerequisites and availability

On-demand and optional invocation paths have different feature eligibility

Limitations

Testing can change application state. Network and identity variants preserve the same assessment objective but require their own authorization and coverage evidence.

Example request

Run the authorized staging penetration test with the stated target, exclusions and test identities.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
