AWS DevOps Agent

Execute an approved mitigation and verify recovery

Carry out an eligible approved change and assess service recovery.

Responsible actor. Authorized incident operator

1. Purpose and scope

An incident owner has accepted a narrowly scoped mitigation and wants to use the documented action path. Confirm Agent Space enablement, the target-account role or connected-tool configuration, and the classification of the operation. Review the actual parameters presented for approval; a broadly named role is not the approval record.

After the operator approves the eligible action, inspect the resulting resource state and the available attribution evidence. Recovery must still be checked against service measurements. If execution is denied, locate the failed gate instead of widening all permissions. This workflow does not convert the earlier mitigation recommendation into standing authorization for subsequent changes.

Inputs
Directed-action enablement, eligible role or integration, correct tool classification and exact operation/resource approval.
Expected output
Attributed action record and independently checked resulting state.
Execution pattern
On demand
Delivery mode
Controlled action

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Authorize and execute the eligible action

    Apply the specific reviewed operation rather than standing authorization.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Operation-specific directed authorization. Execute the specific approved operation through its configured authorization path.

    Configuration. Directed actions

    Effect. Resource or external-tool mutation

    Verification. Inspect exact approval, attribution and resulting resource state.

    Failure handling. Stop on a failed authorization gate; use the normal approved engineering process rather than bypassing it.

  2. Measure post-change service state

    Determine whether the action had its intended effect.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Evidence retrieval through selected tools. Invoke the authorized source with the intended identity, resource and observation period.

    Configuration. Provider registration and selected tools

    Effect. Source read

    Verification. Compare returned identifiers and a material measurement with the original source.

    Failure handling. Report the failed read and withhold conclusions that require that source.

  3. Decide whether recovery is established

    Apply the declared recovery or rollback conditions.

    Responsible actor. Responsible engineer or reviewer

    Dependency. Required. Applies to the selected implementation.

    Implementation. Engineering procedure; no native service operation is asserted for this step.

    Effect. Team decision; no implicit service action

    Verification. Record the decision with the source identifiers and evidence needed for the case completion criteria.

    Failure handling. Keep the result unresolved and assign the missing decision or evidence to an owner.

3. Configuration

Use the applicable configuration below for the selected workflow. Parameters and checks are engineering guidance, not deployable AWS payloads. Product procedures remain in the linked guide sections.

Setup procedure

  1. Inspect each authorization layer without broadening scope.
  2. Review the exact parameters and obtain the documented operator approval.
  3. Compare resulting resource state with service recovery measurements.

Proposed checks

  • An operation outside the approval remains rejected.
  • The action record matches the approved operation and target.
  • Unsuccessful recovery follows the declared rollback or escalation decision.

Stop behavior. Stop when a gate fails. An unconditional elevated-role workaround is not part of this recipe.

Supporting procedures for this configuration

This recipe is reused by multiple workflows. The required, optional, or conditional dependencies for this use case are specified in its workflow above.

4. Verification and limits

Completion criteria

  • Exact operation and target were approved.
  • Attributed resulting state is retained.
  • Recovery is assessed against current service measurements.

Prerequisites and availability

GA operations; directed actions require opt-in

Limitations

Approval is scoped to a particular operation and resource. Tool misclassification can change expected approval behavior.

Example request

After showing the exact target and parameters, request approval for the narrowly scoped change.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
