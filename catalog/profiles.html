Select a product-specific configuration recipe after choosing the operational objective. Profile parameters and acceptance checks are authored guidance; they are not deployable AWS payloads or evidence that a live test ran.

PR-D-INCIDENT · AWS DevOps Agent

Incident and prevention configuration

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
OperationInvestigation, routing, feedback or prevention evaluationSelect the operation matching the objective
Agent SpaceAuthorized space and account scopeApproved staging space
Incident subjectService identity and actual UTC observation intervalCheckout service and supplied incident window
Historical contextRelevant active monitor or service contextOptional; never a substitute for current evidence

Configuration procedure

  1. Verify operator access independently from resource and tool access.
  2. For incident work, start from a signal or scoped manual investigation. For prevention work, inspect a manual or scheduled evaluation over existing investigation evidence.
  3. Inspect triage, current evidence and any observable historical-context retrieval separately.

Acceptance exercises

  • Current observations contradict a prior cause: the conclusion must follow current evidence.
  • A missing source produces an explicit evidence gap.
  • Correcting routing changes linkage, not production resource state.

Stop and lifecycle behavior

Use supported investigation controls. Steering and feedback do not grant mutation authority.

Linked mechanisms

Evidence retrieval through selected tools · Incident routing · Investigation and operator steering · Selective incident-context retrieval · Corrective investigation feedback · Cross-investigation prevention evaluation

Applicable outcomes

Triage incident signals · Investigate a service incident · Prepare a mitigation plan · Identify recurring incident patterns · Prioritize incident-prevention work

PR-D-REPORT · AWS DevOps Agent

Custom operational reporting configuration

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
Resource scopeActual service and resource identifiersApproved service list
Tool selectionExact operations available in the Agent SpaceSelected telemetry, incident or deployment read tools
Reporting basisPeriod, dimensions, aggregation, comparison and failed-read treatmentPrevious complete UTC day with declared percentile and error-rate basis
ContextOnly the relevant procedure and mappingReviewed report skill and explicitly selected store
ScheduleOptional timing separate from observation windowDisabled until a trial invocation passes
PublicationSeparate destination-specific effectNo external destination by default

Configuration procedure

  1. Create the custom definition with explicit objective, output and source limits.
  2. Select actual tools and inspect applicable skills and store access using the current guide.
  3. Run once, inspect the invocation and reconcile material measurements.
  4. Enable recurrence only when schedule variability and concurrency suit the requirement.

Acceptance exercises

  • Unavailable telemetry is missing evidence, not a healthy result.
  • A known mapping is interpreted from the intended context.
  • A delayed invocation exposes both observation time and generation time.

Stop and lifecycle behavior

Pause future triggers and cancel current work separately. Do not claim guaranteed minute-by-minute delivery from a flexible schedule.

Linked mechanisms

Evidence retrieval through selected tools · Configured custom-agent invocation · Runbook applicability and procedural loading · Selective incident-context retrieval · Standing instruction loading · Schedule-to-invocation creation · Environment-knowledge construction and refresh

Applicable outcomes

Prepare an incident-status bulletin · Assess and report service health and trends · Review deployment and change activity · Audit resource configurations against approved standards

PR-D-ACTION · AWS DevOps Agent

Directed mitigation configuration

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
TargetExplicit resource and eligible operationApproved staging resource
AuthorizationOpt-in, role, tool category and exact approvalRecord configuration and approval identifiers
RecoveryPost-change measurements and rollback conditionsDeclared latency and error acceptance

Configuration procedure

  1. Inspect each authorization layer without broadening scope.
  2. Review the exact parameters and obtain the documented operator approval.
  3. Compare resulting resource state with service recovery measurements.

Acceptance exercises

  • An operation outside the approval remains rejected.
  • The action record matches the approved operation and target.
  • Unsuccessful recovery follows the declared rollback or escalation decision.

Stop and lifecycle behavior

Stop when a gate fails. An unconditional elevated-role workaround is not part of this recipe.

Linked mechanisms

Operation-specific directed authorization · Evidence retrieval through selected tools

Applicable outcomes

Execute an approved mitigation and verify recovery

PR-S-ASSESS · AWS Security Agent

Running-application assessment configuration

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
TargetAuthorized application and deployed revisionStaging application / demo-r2
NetworkPublic or private route and explicit exclusionsSeparate attack targets from login support paths
IdentityRepresentative test roles and credential strategyTest customer role; no production credential
Run limitsConfigured work limits and responsible ownerOwner-approved limit, not assumed wall-clock duration

Configuration procedure

  1. Review the saved scope before starting execution.
  2. Test target reachability and actual application identity.
  3. Start a separate run and retain excluded or incomplete paths.
  4. For revalidation, confirm the deployed repair and select original findings rather than run broad discovery.

Acceptance exercises

  • Failed authentication leaves protected paths unassessed.
  • Each run identifies the actual target revision and roles.
  • Revalidation retains the original finding and separate job.

Stop and lifecycle behavior

Stop unexpected effects. Control future schedules separately from current jobs, findings and external tickets.

Linked mechanisms

Application-context assembly · Target scope and network access · Credential resolution and application login · Successful login-procedure reuse · Saved assessment and independent execution · Selected finding replay and lineage

Applicable outcomes

Assess a running application for vulnerabilities · Revalidate a finding after deployment of a repair

PR-S-REVIEW · AWS Security Agent

Source, design and finding-review configuration

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
Assessment modeOne supported assessment with its own resource lifecycleCode baseline, code change, design or threat model
Evidence revisionSource or design matching the subjectImmutable revision identifier
CriteriaReviewed applicable requirementsSelected enabled pack
Write featuresOptional comment, repair proposal or ticketDisabled until provider and audience review

Configuration procedure

  1. Choose the actual mode rather than assume a shared configuration schema.
  2. Connect matching evidence and enable the intended review criteria.
  3. Inspect preflight and completed results separately.
  4. Review repair proposals through ordinary tests and deployment before revalidation.

Acceptance exercises

  • A new source revision cannot silently reuse stale acceptance.
  • A requirement may be inapplicable rather than compliant.
  • Regenerating a pack is reviewed as replacement.

Stop and lifecycle behavior

Retain unfinished findings. Disable optional writes without discarding their source evidence.

Linked mechanisms

Application-context assembly · Full-source or change-focused code assessment · Point-in-time design assessment · System-model construction and threat analysis · Requirement applicability and evaluation · Requirement-pack regeneration · Finding evidence inspection · Repository repair proposal · Finding publication to Jira

Applicable outcomes

Review source code for security issues · Review a proposed application design · Develop and review an application threat model · Triage and prioritize security findings · Prepare a code-remediation proposal · Consolidate and maintain security requirements

PR-S-PIPELINE · AWS Security Agent

Pipeline assessment and delivery decision

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
AssessmentSaved authorized configurationActual assessment configuration identifier
Pipeline identityScoped invocation accessApproved CI identity
Gate policyErrors, incomplete results and accepted findingsBlock or escalate; never a missing-result pass

Configuration procedure

  1. Verify eligibility and bind the pipeline to the saved assessment.
  2. Invoke and observe the server-side job, retaining revision and run identity.
  3. Apply the team gate only after interpreting actual scope and coverage.

Acceptance exercises

  • Invocation failure is not successful assessment.
  • An observation timeout does not imply that the underlying job stopped.
  • A new deployed revision requires matching assessment evidence.

Stop and lifecycle behavior

Stop the actual assessment using supported controls; stopping the pipeline runner is not assumed to cancel it.

Linked mechanisms

Pipeline invocation and result observation · Saved assessment and independent execution

Applicable outcomes

Assess a running application for vulnerabilities

Former catalog labels: CI/CD assessment integration

Cost-analysis and report configuration

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
Query basisDates, metric, currency, scope, dimensions and granularityComplete comparable periods and explicitly chosen cost metric
Analysis typeObserved cost, forecast, coverage or recommendationSelect the required upstream evidence
Organization contextOptional reviewed ownership mappingActive non-sensitive reference file
OutputResult or supported report artifactHTML report retaining source basis

Configuration procedure

  1. Verify the agent data role and relevant upstream service.
  2. State material query choices even when preferences are retained.
  3. Reconcile a material result independently and inspect task or artifact identity.

Acceptance exercises

  • Different filters invalidate a direct numerical comparison.
  • Forecasts and recommendation estimates are not added to observed costs.
  • Missing change evidence leaves causal attribution unresolved.

Stop and lifecycle behavior

Cancel tasks and manage artifacts separately. This recipe authorizes neither infrastructure changes nor commitment purchases.

Linked mechanisms

Source-backed cost analysis · Uploaded reference-file use · Cross-session preference retention · Conversation compaction · Queued task execution and observation · Report generation and revision

Applicable outcomes

Analyze historical cost and usage · Review a cost forecast · Review commitment coverage · Prepare a periodic cost report · Investigate a cost anomaly · Prioritize optimization recommendations · Measure the outcome of an implemented optimization

PR-F-AUTOMATION · AWS FinOps Agent

Recurring or anomaly-triggered FinOps work

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
TriggerSchedule or supported anomaly eventExplicit schedule OR selected Cost Anomaly Detection monitor
Observation windowPeriod independent of execution timePrevious complete calendar week
DestinationOptional and separately reviewedNo external publication by default

Configuration procedure

  1. Verify trigger permissions and source monitor where event-driven.
  2. Inspect the stored automation rather than rely on conversational acknowledgement.
  3. Trace an actual task to its analysis and optional delivery.

Acceptance exercises

  • A nonmatching event creates no expected task.
  • Queue, analysis and publication failures remain distinguishable.
  • Disabling automation stops future starts, not deletion of old tasks.

Linked mechanisms

Applicable outcomes

Prepare a periodic cost report · Investigate a cost anomaly

PR-F-PUBLICATION · AWS FinOps Agent

FinOps destination and authorization configuration

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
DestinationConfigured Jira project or Slack channelReviewed internal test destination
InvocationInteractive, on-demand, scheduled or event-drivenSpecify the path explicitly
Content scopeApproved data and audienceNon-sensitive summary and evidence references

Configuration procedure

  1. Register the provider and bind the agent connection to its destination.
  2. Review audience and message scope before invocation.
  3. For Jira, use invocation-specific approval; for Slack, do not expect a confirmation prompt.
  4. Inspect actual destination and task history.

Acceptance exercises

  • Interactive or on-demand Jira approval is observed where applicable.
  • Automated Jira authorization is reviewed at setup.
  • Slack is treated as direct publication, not as approval-protected.

Stop and lifecycle behavior

Disable future publication or its automation. Disconnecting a destination does not delete already published records.

Linked mechanisms

Invocation-dependent Jira approval · Direct Slack publication

Applicable outcomes

Prepare a periodic cost report · Investigate a cost anomaly · Prioritize optimization recommendations

Configuration procedure

PR-EVIDENCE · AWS DevOps Agent

Cross-tool evidence reconciliation

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
Identity mappingService, resource and revision relationships across toolsReviewed application-to-deployment mapping
Observation windowCommon UTC periodExplicit incident interval

Configuration procedure

  1. Read source identifiers instead of matching only titles.
  2. Join observations using reviewed service and revision mappings.
  3. Retain unmatched records and contradictory evidence.

Acceptance exercises

  • Similar timestamps alone do not establish causality.
  • An observation for the wrong account or revision is rejected.

Stop and lifecycle behavior

Continue only with supported relationships and assign gaps to an owner. This is a team procedure, not a universal native correlation feature.

Linked mechanisms

Evidence retrieval through selected tools · Environment-knowledge construction and refresh

Applicable outcomes

Investigate a service incident · Assess and report service health and trends · Review deployment and change activity · Document service topology and dependencies

Former catalog labels: Cross-tool operational correlation

ParameterPurposeIllustrative value

Configuration procedure

  1. Verify access to the sources needed for this question.
  2. Ask through the built-in query path, stating service and observation scope.

PR-D-PROCEDURE · AWS DevOps Agent

Reviewed runbook-skill configuration

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
Procedure sourceOne approved SOP after conflict resolutionReviewed source in Git
ApplicabilitySymptoms, services and agent scopeSpecific operational situation
Tool referencesReal tool names used by the procedureSelected supported operations

Configuration procedure

  1. Reconcile conflicting SOPs and obtain an accountable review.
  2. Package the approved procedure as a skill with its applicability description.
  3. Keep broadly applicable reporting conventions in standing instructions only where appropriate.
  4. Test a matching and a nonmatching request using non-sensitive evidence.

Acceptance exercises

  • Irrelevant tasks do not require the skill.
  • Required tools exist and unsupported steps stop explicitly.
  • Changes to standing instructions are tested in a new applicable session.

Stop and lifecycle behavior

Deactivate or revise the relevant procedural configuration using the supported controls. Changing a skill does not undo past actions or grant new access.

Linked mechanisms

Runbook applicability and procedural loading · Standing instruction loading

Applicable outcomes

Consolidate and maintain operational procedures

PR-D-KNOWLEDGE · AWS DevOps Agent

Environment-knowledge review configuration

Proposed recipe; verify feature eligibility and substitute approved identifiers.

ParameterPurposeIllustrative value
Environment scopeSelected accounts, services and connected evidenceApproved resource and repository scope
Reference changeKnown deployed relationship to verifyNew dependency and exact revision
Reviewed outputOwner-maintained service descriptionEvidence-linked topology document

Configuration procedure

  1. Verify the relevant discovery and connected sources.
  2. Inspect the managed knowledge refresh and resulting version where available.
  3. Compare a known changed relationship with actual source evidence.
  4. Maintain the owner-reviewed description with unresolved relationships identified.

Acceptance exercises

  • An inferred edge remains distinguishable from an observed relationship.
  • A submitted refresh is not treated as completed knowledge production.
  • A missing graph resource is not automatically interpreted as denied direct access.

Stop and lifecycle behavior

Do not widen permissions to conceal a representation gap. Use authoritative source evidence and record unverified context.

Linked mechanisms

Environment-knowledge construction and refresh · Evidence retrieval through selected tools · Selective incident-context retrieval

Applicable outcomes

Document service topology and dependencies
