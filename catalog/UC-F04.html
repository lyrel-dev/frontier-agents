Use cases/Cost reporting

AWS FinOps Agent

Prepare a periodic cost report

Produce a comparable report for the defined period and audience.

Responsible actor. FinOps reporting owner

1. Purpose and scope

The team needs a recurring cost report with a stable comparison basis. Define the reporting period, sections, dimensions, audience, and output format before scheduling it. The task should distinguish observed spend, anomalies, and source recommendation estimates so unlike values are not added together.

Review a trial artifact against the source totals and inspect the saved automation separately from the generated task. A weekly schedule does not specify whether the report includes an incomplete current day. Preserve the task identifier and query basis with each report so changes in the template do not obscure what was actually compared.

Inputs
Report contract, schedule, source scope, context and recipients.
Expected output
HTML, PDF or editable presentation artifact.
Execution pattern
Scheduled
Delivery mode
Configured recurring task

Variants

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Read report evidence

    Retrieve the declared period and comparison dimensions.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Source-backed cost analysis. Read the relevant upstream service and interpret its returned evidence.

    Configuration. Cost and operational source access

    Effect. Source read

    Verification. Reconcile a material result using the same dates, metric, scope and dimensions.

    Failure handling. Withhold unsupported numerical or causal conclusions and identify missing sources.

  2. Apply approved reporting context

    Use maintained mappings and template.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Optional. Organization-specific reference material is selected.

    Platform process. Uploaded reference-file use. Read the maintained mapping or reporting convention during relevant work.

    Configuration. Context files

    Effect. Context read

    Verification. Verify a known mapping and expose unmapped records.

    Failure handling. Keep unassigned values visible and update the authoritative file deliberately.

  3. Run the report task

    Retain a separate execution identity.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Queued task execution and observation. Run queued work and retain its separate execution evidence.

    Configuration. Task queue and history

    Effect. Execution and output

    Verification. Match completed results to task identity and requested scope.

    Failure handling. Distinguish absent, queued and failed tasks before retrying.

  4. Generate the reviewed artifact

    Provide the requested supported output format.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Report generation and revision. Format supported output and revise it without silently changing analytical scope.

    Configuration. Report artifacts

    Effect. Report artifact

    Verification. Compare displayed figures and period with the reviewed source analysis.

    Failure handling. Do not distribute an artifact that no longer matches its query basis.

  5. Repeat on a schedule

    Create future reports under the same basis.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Conditional. Recurring execution is enabled.

    Platform process. Scheduled task creation. Create a new task on each applicable scheduled occurrence.

    Configuration. Scheduled and event automations · Task queue and history

    Effect. Future tasks

    Verification. Inspect trigger and the actual task's reporting window separately.

    Failure handling. Disable future starts and control already-created work separately.

  6. Publish to the configured Jira destination

    Create the supported report follow-up in the approved project.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Optional. Jira distribution is selected and invocation-specific authorization is satisfied.

    Platform process. Invocation-dependent Jira approval. Request approval interactively or on demand; use setup authorization for scheduled or event-driven actions.

    Configuration. Jira issue and comment actions

    Effect. External publication

    Verification. Inspect invocation type, action details, destination and resulting issue or comment.

    Failure handling. Stop incorrect destinations. Do not expect an interactive prompt to protect an unattended automation.

  7. Publish to the configured Slack channel

    Deliver the permitted report summary to its reviewed audience.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Optional. Slack distribution is selected; audience review occurs before direct publication.

    Platform process. Direct Slack publication. Post to the configured channel without a per-message approval prompt.

    Configuration. Slack message publication

    Effect. External publication

    Verification. Review audience before invocation and inspect delivery afterward.

    Failure handling. Keep analysis completion separate from delivery failure; posting does not establish channel-reading capability.

3. Configuration

Use the applicable configuration below for the selected workflow. Parameters and checks are engineering guidance, not deployable AWS payloads. Product procedures remain in the linked guide sections.

Cost-analysis and report configuration

ParameterConfiguration decisionExample or constraint
Query basisDates, metric, currency, scope, dimensions and granularityComplete comparable periods and explicitly chosen cost metric
Analysis typeObserved cost, forecast, coverage or recommendationSelect the required upstream evidence
Organization contextOptional reviewed ownership mappingActive non-sensitive reference file
OutputResult or supported report artifactHTML report retaining source basis

Setup procedure

  1. Verify the agent data role and relevant upstream service.
  2. State material query choices even when preferences are retained.
  3. Reconcile a material result independently and inspect task or artifact identity.

Proposed checks

  • Different filters invalidate a direct numerical comparison.
  • Forecasts and recommendation estimates are not added to observed costs.
  • Missing change evidence leaves causal attribution unresolved.

Stop behavior. Cancel tasks and manage artifacts separately. This recipe authorizes neither infrastructure changes nor commitment purchases.

Setup procedure

  1. Register the provider and bind the agent connection to its destination.
  2. Review audience and message scope before invocation.
  3. For Jira, use invocation-specific approval; for Slack, do not expect a confirmation prompt.
  4. Inspect actual destination and task history.

Proposed checks

  • Interactive or on-demand Jira approval is observed where applicable.
  • Automated Jira authorization is reviewed at setup.
  • Slack is treated as direct publication, not as approval-protected.

Stop behavior. Disable future publication or its automation. Disconnecting a destination does not delete already published records.

4. Verification and limits

Completion criteria

  • Period and cost basis remain consistent.
  • Observed values, projections and estimates are separated.
  • The artifact matches its reviewed task and source evidence.

Prerequisites and availability

Preview

Limitations

Schedule, source window and audience are separate settings. Report values still require reconciliation.

Example request

Create a weekly cost report with service totals, anomalies, recommendations, owners and unresolved gaps.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
