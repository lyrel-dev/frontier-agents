AWS Security Agent

Develop and review an application threat model

Produce a reviewed system representation and evidence-backed threats for a defined scope.

Responsible actor. Threat-model reviewer

1. Purpose and scope

A service boundary has changed and the team needs an updated threat model. Supply explicit scope documents and the relevant architecture and source evidence. Review the inferred system overview, components, data flows, and trust boundaries before evaluating individual threats.

Correct an incorrect boundary at the model input rather than dismissing every threat that follows from it. Retain evidence for the accepted threats and identify inferred relationships that remain unverified. The result is a reviewed model for that scope and run, not proof that every possible threat has been discovered.

Inputs
Architecture documents, code/context sources and explicit system boundary.
Expected output
Assets, trust boundaries, flows, threats and model findings.
Execution pattern
On demand
Delivery mode
Preview assessment

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Assemble scope and source inputs

    Separate analytical focus from implementation context.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Application-context assembly. Read the connected source and documentation relevant to the selected assessment.

    Configuration. Application sources and integrations

    Effect. Source read

    Verification. Compare source revision and system boundary with the intended subject.

    Failure handling. Exclude mismatched context and document the resulting assessment limitation.

  2. Construct and review the model

    Examine system boundaries before individual threats.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. System-model construction and threat analysis. Construct the system model and examine threats to its flows and boundaries.

    Configuration. Threat-model configurations · Application sources and integrations

    Effect. Model result

    Verification. Review inferred boundaries before interpreting individual threats.

    Failure handling. Correct input scope when the model represents the wrong system.

  3. Resolve model assumptions

    Correct inputs and assign unresolved relationships to owners.

    Responsible actor. Responsible engineer or reviewer

    Dependency. Required. Applies to the selected implementation.

    Implementation. Engineering procedure; no native service operation is asserted for this step.

    Effect. Team decision; no implicit service action

    Verification. Record the decision with the source identifiers and evidence needed for the case completion criteria.

    Failure handling. Keep the result unresolved and assign the missing decision or evidence to an owner.

3. Configuration

Use the applicable configuration below for the selected workflow. Parameters and checks are engineering guidance, not deployable AWS payloads. Product procedures remain in the linked guide sections.

Write featuresOptional comment, repair proposal or ticketDisabled until provider and audience review

Setup procedure

  1. Choose the actual mode rather than assume a shared configuration schema.
  2. Connect matching evidence and enable the intended review criteria.
  3. Inspect preflight and completed results separately.
  4. Review repair proposals through ordinary tests and deployment before revalidation.

Proposed checks

  • A new source revision cannot silently reuse stale acceptance.
  • A requirement may be inapplicable rather than compliant.
  • Regenerating a pack is reviewed as replacement.

Stop behavior. Retain unfinished findings. Disable optional writes without discarding their source evidence.

4. Verification and limits

Completion criteria

  • Boundaries and flows are reviewed before threats.
  • Source assumptions and inferred edges remain visible.
  • Threat dispositions refer to the selected model run.

Prerequisites and availability

Preview

Limitations

Inferred system context requires review; the model is not a complete guarantee of threat coverage.

Example request

Create a threat model for the checkout service and mark inferred flows that require owner confirmation.
