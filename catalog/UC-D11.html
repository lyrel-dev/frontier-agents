AWS DevOps Agent

Document service topology and dependencies

Produce a reviewed service and dependency description.

Responsible actor. Service owner

1. Purpose and scope

A service owner needs an architecture description before changing a dependency. Start from discovered resources and the topology’s service, repository, pipeline, and dependency relationships. Compare those relationships with the deployed configuration and source revision, distinguishing directly observed relationships from inferred ones.

Write the reviewed result as a maintained service description with identifiers, evidence links, and unresolved edges. The topology is useful input to that document, but it is not a guaranteed complete inventory or an automatic update to the team’s architecture repository. This use case produces owner-reviewed documentation; the following refresh use case checks whether the underlying environment model has changed.

Inputs
Connected accounts, discovery, Resource Explorer where applicable and relevant integrations.
Expected output
Topology view and environment summary that can support architecture documentation.
Execution pattern
On demand or refreshed
Delivery mode
Built-in function with composed documentation

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Inspect environment consolidation

    Use discovery and the resulting retained representation.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Environment-knowledge construction and refresh. Synthesize environment evidence into service, dependency and delivery context for subsequent work.

    Configuration. Resource discovery and topology · Memory stores and entries

    Effect. Retained context update

    Verification. Check a known changed resource and relationship in the resulting version.

    Failure handling. Mark stale or inferred relationships; do not substitute the graph for current configuration.

  2. Check important source relationships

    Compare graph edges with deployment and source evidence.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Evidence retrieval through selected tools. Invoke the authorized source with the intended identity, resource and observation period.

    Configuration. Provider registration and selected tools

    Effect. Source read

    Verification. Compare returned identifiers and a material measurement with the original source.

    Failure handling. Report the failed read and withhold conclusions that require that source.

  3. Maintain the reviewed description

    Record owner-verified relationships and unresolved discrepancies.

    Responsible actor. Responsible engineer or reviewer

    Dependency. Required. Applies to the selected implementation.

    Implementation. Engineering procedure; no native service operation is asserted for this step.

    Effect. Team decision; no implicit service action

    Verification. Record the decision with the source identifiers and evidence needed for the case completion criteria.

    Failure handling. Keep the result unresolved and assign the missing decision or evidence to an owner.

3. Configuration

Use the applicable configuration below for the selected workflow. Parameters and checks are engineering guidance, not deployable AWS payloads. Product procedures remain in the linked guide sections.

Environment-knowledge review configuration

ParameterConfiguration decisionExample or constraint
Environment scopeSelected accounts, services and connected evidenceApproved resource and repository scope
Reference changeKnown deployed relationship to verifyNew dependency and exact revision
Reviewed outputOwner-maintained service descriptionEvidence-linked topology document

Setup procedure

  1. Verify the relevant discovery and connected sources.
  2. Inspect the managed knowledge refresh and resulting version where available.
  3. Compare a known changed relationship with actual source evidence.
  4. Maintain the owner-reviewed description with unresolved relationships identified.

Proposed checks

  • An inferred edge remains distinguishable from an observed relationship.
  • A submitted refresh is not treated as completed knowledge production.
  • A missing graph resource is not automatically interpreted as denied direct access.

Stop behavior. Do not widen permissions to conceal a representation gap. Use authoritative source evidence and record unverified context.

ParameterConfiguration decisionExample or constraint

Setup procedure

  1. Read source identifiers instead of matching only titles.
  2. Join observations using reviewed service and revision mappings.
  3. Retain unmatched records and contradictory evidence.

Proposed checks

  • Similar timestamps alone do not establish causality.
  • An observation for the wrong account or revision is rejected.

Stop behavior. Continue only with supported relationships and assign gaps to an owner. This is a team procedure, not a universal native correlation feature.

4. Verification and limits

Completion criteria

  • Observed and inferred relationships are distinguished.
  • Deployed revision and evidence are recorded.
  • Unresolved relationships have owners.

Prerequisites and availability

GA production operations

Limitations

Topology is a representation, not an authorization boundary or guaranteed complete inventory.

Example request

Document the payments service containers, downstream dependencies, repositories and deployment boundaries; mark inferred relationships.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
