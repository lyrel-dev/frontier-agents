AWS DevOps Agent

Prepare an incident-status bulletin

Explain what changed in an active incident during a short observation window.

Responsible actor. Incident commander

1. Purpose and scope

During an active incident, the incident commander needs a brief update that explains what has changed since the preceding observation. Configure a specialist task with the incident identifier, selected telemetry tools, and a short explicit lookback window. Ask for changed measurements, the status of open hypotheses, missing reads, and the next check rather than a repetition of the whole incident history.

A report can analyze minute-resolution measurements without arriving every minute. The documented custom-agent schedule uses a flexible window of up to 30 minutes; execution time is additional. For time-critical updates, invoke the task on demand or use a separately tested triggering design. Record both the measurement window and report-generation time so a delayed bulletin is not mistaken for current telemetry.

Inputs
Custom agent, selected telemetry and incident tools, explicit five- or ten-minute window and output contract.
Expected output
Delta-focused status update: changed observations, open hypotheses, owner and next check.
Execution pattern
On demand; scheduling is not exact-minute
Delivery mode
Configured custom agent

Variants

On-demand bulletin

Invoke for a specific lookback period.

Execution may lag the measurement window.

Recurring bulletin

Configure a supported trigger.

Flexible scheduling does not guarantee minute-by-minute delivery.

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Read the current incident signals

    Obtain the measurements for the declared short window.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Evidence retrieval through selected tools. Invoke the authorized source with the intended identity, resource and observation period.

    Configuration. Provider registration and selected tools

    Effect. Source read

    Verification. Compare returned identifiers and a material measurement with the original source.

    Failure handling. Report the failed read and withhold conclusions that require that source.

  2. Prepare a delta-focused bulletin

    Use the configured reporting procedure and inspect its invocation.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Configured custom-agent invocation. Execute the selected operational work and retain its invocation trajectory.

    Configuration. Custom-agent definitions · Invocation history and trajectories

    Effect. Execution and output

    Verification. Inspect tool arguments, failures and output against the task scope.

    Failure handling. Mark incomplete output and resolve the failed prerequisite before repeating the run.

  3. Create recurring bulletin work

    Repeat only within accepted timing constraints.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Conditional. A non-real-time recurring profile is approved.

    Platform process. Schedule-to-invocation creation. Create future work under the supported scheduling and concurrency constraints.

    Configuration. Custom-agent schedule triggers · Invocation history and trajectories

    Effect. Future invocation

    Verification. Inspect saved timing and actual start; record the observation window independently.

    Failure handling. Use explicit invocation when timing is critical. Pausing future starts does not cancel current work.

Setup procedure

  1. Create the custom definition with explicit objective, output and source limits.
  2. Select actual tools and inspect applicable skills and store access using the current guide.
  3. Run once, inspect the invocation and reconcile material measurements.
  4. Enable recurrence only when schedule variability and concurrency suit the requirement.

Proposed checks

  • Unavailable telemetry is missing evidence, not a healthy result.
  • A known mapping is interpreted from the intended context.
  • A delayed invocation exposes both observation time and generation time.

Stop behavior. Pause future triggers and cancel current work separately. Do not claim guaranteed minute-by-minute delivery from a flexible schedule.

4. Verification and limits

Completion criteria

  • Incident and measurement window are identified.
  • Changed facts, hypotheses and next check are stated.
  • Generation time is distinguished from observation time.

Prerequisites and availability

GA custom agents

Limitations

Telemetry resolution, lookback period, schedule window, and execution time are different. The documented custom-agent schedule has a flexible window of up to 30 minutes.

Example request

Report what changed in the active incident during the previous five complete minutes, including the observation window, generation time, and missing sources.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
