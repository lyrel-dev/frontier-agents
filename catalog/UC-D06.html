Use cases/Operational reporting

AWS DevOps Agent

Assess and report service health and trends

Produce a sourced health assessment or comparable-period report.

Responsible actor. On-call or service engineer

1. Purpose and scope

The incoming engineer needs to know whether the service is healthy, what changed, and which observations are missing. Define the service scope and reporting period first. Retrieve the selected measurements, compare significant differences with a baseline when needed, and connect material observations to incident and deployment evidence. A recent snapshot and a multiweek trend are analytical profiles of the same reporting objective.

Review a material measurement against its source before relying on the report. Keep missing telemetry visible and consider workload changes before interpreting a trend. Recurrence preserves the agreed reporting basis; it does not create a different objective. An operational review can subsequently use this report to decide priorities and owners.

Inputs
Service identity, complete periods, selected telemetry tools and report instructions; optional relevant context.
Expected output
Sourced health snapshot, period comparison or trend report.
Execution pattern
On demand or scheduled
Delivery mode
Native inquiry or configured reporting

Variants

Current snapshot

A bounded recent observation of the selected service.

An unavailable source is a gap, not a healthy measurement.

Period or trend comparison

Compare complete periods under the same dimensions and aggregation.

Check denominator, traffic composition and source completeness.

Recurring service report

Run a reviewed definition repeatedly.

Schedule, observation window and destination remain separate settings.

2. Workflow

The workflow order, acceptance criteria and failure decisions are authored engineering guidance. Each mechanism links to documented service behavior and concrete configuration features.

  1. Retrieve comparable measurements

    Read logs, metrics and incidents under one reporting basis.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Required. Applies to the selected implementation.

    Platform process. Evidence retrieval through selected tools. Invoke the authorized source with the intended identity, resource and observation period.

    Configuration. Provider registration and selected tools

    Effect. Source read

    Verification. Compare returned identifiers and a material measurement with the original source.

    Failure handling. Report the failed read and withhold conclusions that require that source.

  2. Answer a native health inquiry

    Use the built-in query path for the native snapshot profile.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Conditional. The built-in conversational snapshot profile is selected.

    Platform process. Built-in operational inquiry. Use the built-in on-demand inquiry path to answer the operational question using available authorized evidence.

    Configuration. On-demand operational queries · Provider registration and selected tools

    Effect. Source read and conversational result

    Verification. Inspect scope and reproduce a material observation from the same source query.

    Failure handling. Name the missing source and qualify or withhold the answer; creating a custom agent does not by itself repair source access.

  3. Interpret retained service context

    Resolve known mappings or relationships when relevant.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Optional. The report uses maintained service context.

    Platform process. Selective incident-context retrieval. Select a relevant store, inspect its entries and read the content needed by the current task.

    Configuration. Memory stores and entries

    Effect. Context read

    Verification. Distinguish entry existence, observable retrieval and correctness against current evidence.

    Failure handling. Continue without history when current evidence suffices. Do not infer retrieval merely from answer wording.

  4. Run the reporting definition

    Produce the configured snapshot, comparison or trend report.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Conditional. A configured snapshot, comparison or recurring-report profile is selected.

    Platform process. Configured custom-agent invocation. Execute the selected operational work and retain its invocation trajectory.

    Configuration. Custom-agent definitions · Invocation history and trajectories

    Effect. Execution and output

    Verification. Inspect tool arguments, failures and output against the task scope.

    Failure handling. Mark incomplete output and resolve the failed prerequisite before repeating the run.

  5. Create recurring invocations

    Repeat the reporting contract without changing its basis.

    Responsible actor. Service execution; accountable engineer reviews the result

    Dependency. Conditional. Recurring execution of the configured reporting profile is selected.

    Platform process. Schedule-to-invocation creation. Create future work under the supported scheduling and concurrency constraints.

    Configuration. Custom-agent schedule triggers · Invocation history and trajectories

    Effect. Future invocation

    Verification. Inspect saved timing and actual start; record the observation window independently.

    Failure handling. Use explicit invocation when timing is critical. Pausing future starts does not cancel current work.

3. Configuration

Use the applicable configuration below for the selected workflow. Parameters and checks are engineering guidance, not deployable AWS payloads. Product procedures remain in the linked guide sections.

Native operational-query configuration

ParameterConfiguration decisionExample or constraint
Agent SpaceOperator and data access for the relevant environmentApproved space
Question scopeActual service, UTC interval and dimensionsDeclared recent observation period

Setup procedure

  1. Verify access to the sources needed for this question.
  2. Ask through the built-in query path, stating service and observation scope.
  3. Inspect returned evidence and reconcile a material observation.

Proposed checks

  • A missing signal is disclosed rather than interpreted as healthy.
  • The answer uses the requested window and dimensions.

Stop behavior. End or redirect an unsupported inquiry. No custom-agent schedule or external publication is implied.

Custom operational reporting configuration

ParameterConfiguration decisionExample or constraint
Resource scopeActual service and resource identifiersApproved service list
Tool selectionExact operations available in the Agent SpaceSelected telemetry, incident or deployment read tools
Reporting basisPeriod, dimensions, aggregation, comparison and failed-read treatmentPrevious complete UTC day with declared percentile and error-rate basis
ContextOnly the relevant procedure and mappingReviewed report skill and explicitly selected store
ScheduleOptional timing separate from observation windowDisabled until a trial invocation passes
PublicationSeparate destination-specific effectNo external destination by default

Setup procedure

  1. Create the custom definition with explicit objective, output and source limits.
  2. Select actual tools and inspect applicable skills and store access using the current guide.
  3. Run once, inspect the invocation and reconcile material measurements.
  4. Enable recurrence only when schedule variability and concurrency suit the requirement.

Proposed checks

  • Unavailable telemetry is missing evidence, not a healthy result.
  • A known mapping is interpreted from the intended context.
  • A delayed invocation exposes both observation time and generation time.

Stop behavior. Pause future triggers and cancel current work separately. Do not claim guaranteed minute-by-minute delivery from a flexible schedule.

Cross-tool evidence reconciliation

ParameterConfiguration decisionExample or constraint
Identity mappingService, resource and revision relationships across toolsReviewed application-to-deployment mapping
Observation windowCommon UTC periodExplicit incident interval

Setup procedure

  1. Read source identifiers instead of matching only titles.
  2. Join observations using reviewed service and revision mappings.
  3. Retain unmatched records and contradictory evidence.

Proposed checks

  • Similar timestamps alone do not establish causality.
  • An observation for the wrong account or revision is rejected.

Stop behavior. Continue only with supported relationships and assign gaps to an owner. This is a team procedure, not a universal native correlation feature.

4. Verification and limits

Completion criteria

  • Service dimensions and observation periods are explicit.
  • Material measurements reconcile with source queries.
  • Missing data and workload-mix changes are disclosed.

Prerequisites and availability

Selected native or custom-agent path; inspect feature-specific eligibility

Limitations

A conversational health answer does not replace monitoring or prove complete signal coverage.

Example request

Report service health for the declared period and comparison basis, showing material changes and unavailable signals.

Verification procedures are proposed checks. This documentation does not report a live execution of the workflow.
