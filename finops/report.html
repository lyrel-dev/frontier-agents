01 / Decision brief

Cost analysis, anomaly investigation, reporting and engineering follow-up.

The first question after a cost increase is not which resource to delete. It is whether the compared figures use the same period, account scope, currency and cost basis. Only then can the team decide whether the movement reflects usage, pricing, allocation, a change in workload behavior or incomplete data.

This report follows a synthetic storage-cost increase from reconciliation to a service-owned action. FinOps Agent can support inquiry, anomaly investigation, recommendation triage and reporting through permitted cost services. The analysis does not authorize a capacity change or purchase. Potential savings remain estimates until an implemented change is measured on a comparable basis.

Recommended starting decision

Start with one cost question whose total can be independently reproduced. Keep infrastructure changes and financial commitments outside the analysis authority.

Audience
FinOps practitioners, platform engineers and service owners
Availability
The entire service is preview. Review the documented US storage and inference boundary before supplying organizational data.

02 / Running example

Explain a synthetic storage-cost increase

Illustrative scenario, not an observed customer result or an executed demonstration.

Trigger
A teaching dataset compares two complete 14-day periods and shows approximately 41% higher cost.
Scope
Explicit accounts, Regions, currency, date boundaries, tags and cost metric; synthetic figures are not an AWS account result.
Deliverable
A reconciled explanation, confidence and gaps, an engineering owner and a controlled follow-up.
Not done

An attractive savings estimate is quoted without matching totals or checking operational constraints.

Done means

The source total is reproducible, the driver is supported by evidence, and an owner accepts the next action and measurement plan.

01

Define the comparison before asking for an explanation

Related capabilities: C01 · C09

Operation and evidence context

Write down the cost metric, currency, account group, Region filters and complete date windows. Clarify whether the comparison includes credits, refunds, amortization or allocation rules. Organizational context can identify owners and services, but it does not repair inconsistent billing filters.

Approve preview use and the documented processing boundary before uploading internal context. IAM and permitted cost services determine accessible data. Start with an account group whose owner can validate a material total rather than granting broad access to make every possible question answerable.

02

Reconcile the total and identify material contributors

Related capabilities: C01 · C02

Operation and evidence context

Ask the agent to group the cost by useful dimensions and show the arithmetic behind the movement. Reproduce at least one material total in the source system using the same filters. A convincing explanation based on a different cost basis is not acceptable evidence.

Forecasts and commitment coverage can provide additional context, but they answer different questions from historical reconciliation. Separate observed spend from forecast values and contractual estimates. The synthetic demo illustrates this distinction; it is not evidence of a real account anomaly.

Responsible role (proposed)
FinOps analyst
Required input and scope
Matching cost queries for both comparison periods.
Review record to retain (proposed)
A reconciled delta and a ranked set of contributing services or usage dimensions.
Independent acceptance gate
Totals, scope and arithmetic agree with an independent source check.
Failure / fallback
Label unresolved discrepancies and withhold a causal conclusion until the totals are understood.

03

Investigate drivers without mistaking correlation for cause

Related capabilities: C03 · C08

Operation and evidence context

An anomaly investigation can combine cost evidence with permitted operational context, including relevant change records. Ask which observations support a likely driver, which alternatives remain plausible, and which evidence is missing. A deployment occurring near the increase is a lead, not proof of causation.

Event-triggered investigation is a configured workflow. Confirm the anomaly event source, permissions and output destination, and decide how duplicate or incomplete events are handled. The team still needs an owner who reviews the result and can stop a noisy automation.

Responsible role (proposed)
Engineering and FinOps owners
Required input and scope
Reconciled movement, anomaly details and permitted change context.
Review record to retain (proposed)
A driver analysis that separates observations, hypotheses and gaps.
Independent acceptance gate
The proposed explanation accounts for a material part of the observed change.
Failure / fallback
Route an unresolved question to the workload owner instead of inventing a definitive cause.

04

Evaluate recommendations against operational constraints

Related capabilities: C04 · C13

Operation and evidence context

Existing optimization recommendations can help prioritize investigation, but their projected savings are not an instruction to implement. Review utilization, resilience, performance and recovery requirements with the service owner. Avoid adding overlapping estimates as though every action can deliver its full saving independently.

For a storage recommendation, clarify whether the action changes retention, retrieval latency, durability assumptions or recovery procedures. The authorized change belongs in normal infrastructure and financial processes. The agent's useful output is a justified candidate with constraints and evidence.

Responsible role (proposed)
Service owner and FinOps reviewer
Required input and scope
Recommendation source, utilization evidence, service constraints and estimated benefit.
Review record to retain (proposed)
A prioritized candidate with operational risks, owner and acceptance criteria.
Independent acceptance gate
The service owner accepts the trade-offs and the change is approved separately.
Failure / fallback
Reject or defer recommendations that conflict with the service's reliability or data obligations.

05

Publish the result to the right audience

Related capabilities: C05 · C06 · C07 · C10 · C11 · C12

Operation and evidence context

Turn the analysis into a report or tracked task with the comparison basis, important figures, uncertainty and next owner. Recurring reporting is useful when its schedule and audience are explicit. Context files and remembered preferences should be reviewed when ownership or reporting rules change.

Jira and Slack are external publication effects, not merely read-only analysis. Interactive Jira confirmation, automated-task behavior and Slack posting controls differ. Review the documented path and the destination audience before scheduling a task or sharing commercially sensitive cost information.

06

Measure an implemented change on a comparable basis

Related capabilities: C13

Operation and evidence context

After an independently authorized engineering change, compare the relevant cost and service indicators using a consistent measurement basis. Separate savings caused by the change from lower traffic, different prices or changed allocation. A smaller invoice alone does not establish that the recommendation delivered the estimated benefit.

Close the task only when the owner has reviewed both cost and operational outcomes. Capture rejected recommendations and analysis effort as well as accepted work. That gives the pilot a more meaningful scorecard than the number of reports produced or the sum of potential savings shown.

Responsible role (proposed)
Engineering owner and cost owner
Required input and scope
Implemented change record, comparable observation windows and service-health evidence.
Review record to retain (proposed)
A measured outcome with attribution limits and an owner-approved disposition.
Independent acceptance gate
Benefit and reliability implications are checked independently of the original recommendation.
Failure / fallback
Leave benefit unclaimed when the comparison cannot isolate the effect or required data is incomplete.

05 / Controls and handoff

Accept the artifact; authorize the effect separately.

Use the DevOps report for an operational incident rather than treating cost analysis as a general incident responder. Use the architecture report for the controlled change handoff.

Illustrative work contract

Product-neutral template. It is not a native agent configuration file, a credential container or an authorization token.

analysis: COST-DEMO-001
data_kind: synthetic-teaching-fixture
periods: two-complete-14-day-windows
metric: stated-cost-basis
owner: service-owner
allowed_effects: [analyze-cost, draft-recommendation]
change_authority: separate-approval
benefit: estimate-until-independently-measured

Authorization and evidentiary limits

A generated recommendation, PR, finding or cost report is evidence for a decision. It is not a universal approval to act in another product.

Verify current feature availability, integration permissions and target safety before using a workflow. Preserve unresolved evidence gaps and use the existing team process when a configured path is not available.

These are proposed engineering controls, not a claim of one shared AWS permission model.

Mechanisms / setup and verification extension

How this platform uses context and executes work

A cost explanation combines retrieved account data, maintained organization files and remembered preferences or corrections. A remembered explanation is not a newly verified cost driver. Reconcile the data window and cost basis each time before acting on an interpretation.

Conversation corrections and investigation outcomes can become agent-specific memory. Uploaded context supplies maintained organization definitions. Scheduled or event-triggered tasks use that context but do not confer permission to resize infrastructure.
