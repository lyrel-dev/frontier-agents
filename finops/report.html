AWS FinOps Agent

Cost-data access, investigation, recommendation retrieval and reporting

A technical reference for cloud-cost engineers and application owners. The agent is an interface over billing and optimization services, with its own tasks, context and publishing actions. It does not become the source of billing truth, independently generate every optimization recommendation, or execute infrastructure rightsizing.

Present · 31:30Editable PowerPointMarkdown reference

Presentation includes 8:00 of prepared-result demonstration. Preparation, service processing time and questions are additional.

Availability and scope

The whole service is in preview. The cited guidance places the agent and stored data in us-east-1 and permits inference processing within the US geography. Storage location, inference location and the regions of analyzed resources are different concepts.

Billing-data inquiry

Retrieve measured spend, predictions and commitment metrics without confusing their meanings.

F01Preview

Retrieve and group historical costs and usage

The agent queries Cost Explorer and related permitted billing tools, then presents the selected data as totals and breakdowns. It can translate a natural-language request into source queries, but the underlying billing services remain the authority for the amounts.

Input

A billing question with account scope, period, granularity, cost metric and requested dimensions such as service, region or tag.

Output and interpretation

A scoped cost or usage result, often with a table or chart. Missing permissions can make a source unavailable; that is not equivalent to zero spend.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Ask in Chat for a specific interval and breakdown. Inspect the query/tool activity and restate the chosen scope in any resulting report.

Limitations and effects

Different cost metrics, date boundaries, currencies or filters can produce different totals. Tags and owner mappings do not guarantee that all spend is attributable.

Proposed operator verification — not an executed test

Reconcile the aggregate and at least one material group against Cost Explorer with identical settings. Require an explicit unallocated or unknown category rather than silently excluding unmatched accounts.

Official documentation: Cost inquiry · Action-specific guardrails and accuracy limits
F02Preview

Retrieve a cost forecast

The agent exposes forecasting data available from Cost Explorer. A forecast is a modeled estimate for a future interval, not a bill or a measured saving. The report must retain the forecast's horizon and source assumptions rather than presenting a single number as a guaranteed outcome.

Input

The account and cost scope, forecast horizon and requested comparison with measured spend.

Output and interpretation

Forecast values and available uncertainty information from the underlying source, distinct from actual cost observations.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Request the forecast for the named scope and period in Chat, then inspect the source response and how it is represented in a chart or report.

Limitations and effects

A forecast does not authorize a budget or a commitment purchase. A changed workload can make a historical pattern a poor guide to the next period.

Proposed operator verification — not an executed test

Label actuals and forecast separately; verify the boundary between completed and future periods. Do not manufacture an uncertainty range when the returned source result does not supply one.

Official documentation: Cost inquiry · Action-specific guardrails and accuracy limits
F03Preview

Inspect commitment coverage, utilization and purchase recommendations

The agent retrieves commitment-related data available through the permitted billing tools. Coverage asks how much eligible usage is covered; utilization asks how much purchased commitment was used. A purchase recommendation is a separate proposed financial decision based on the source service's assumptions.

Input

The relevant Savings Plans or Reserved Instances scope and period, plus the requested coverage, utilization or recommendation view.

Output and interpretation

Source-derived commitment metrics or recommendation details. The guide does not equate a low coverage number with a requirement to buy more commitment.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

State which metric is required and request its scope and period with the answer. Review purchase recommendations separately from historical coverage and utilization.

Limitations and effects

The same purchase can increase coverage while creating underutilization if demand falls. The agent's answer is not a purchase execution or proof that future usage will match the assumed baseline.

Proposed operator verification — not an executed test

Have the responsible cost owner verify commitment term, payment option, eligible usage and demand assumptions in the source tool before any purchase process proceeds.

Official documentation: Cost inquiry

Change and anomaly investigation

Explain a selected comparison or a detector-generated event while preserving uncertainty about cause.

F04Preview

Compare periods and investigate cost drivers

The agent retrieves scoped data and investigates which dimensions account for a cost change. Usage quantity, effective rate, resource mix and billing adjustments are different candidate explanations. A percentage increase in an aggregate is not itself a cause.

Input

Two explicitly comparable periods and the service/account/region or usage-type breakdown needed to explain their difference.

Output and interpretation

A comparison and candidate drivers linked to the retrieved data. A defensible analysis retains an unexplained residual when available dimensions cannot reconcile the full difference.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Ask for the absolute and relative change, the contribution of each returned dimension and the remaining unexplained amount. Request usage and rate evidence before attributing the change to either.

Limitations and effects

Unequal periods, cost-basis changes and incomplete attribution can create misleading comparisons. A cost increase near a deployment is temporal correlation until the relevant resource or usage effect is shown.

Proposed operator verification — not an executed test

Recalculate totals and contributions independently. If quantity/rate fields are unavailable, report that the split cannot be established instead of inferring it from total cost alone.

Official documentation: Cost inquiry · Cost anomaly detection and investigation · Action-specific guardrails and accuracy limits
F05Preview

Investigate a Cost Anomaly Detection event

The agent retrieves anomaly details, ranks contributing dimensions and investigates likely drivers. It can correlate cost data with CloudTrail activity when permitted. Detection originates in AWS Cost Anomaly Detection; the agent does not replace the monitor or guarantee the causal explanation.

Input

An existing cost anomaly or a matching detector event, the monitor identity and accessible billing evidence; CloudTrail access is optional supporting context.

Output and interpretation

An investigation linked to the anomaly, affected scope and candidate causes, with task history when run asynchronously.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Request analysis of a specific anomaly, or configure a cost-anomaly event automation for selected monitors and thresholds.

Limitations and effects

An absent or inaccessible CloudTrail event cannot prove that no change occurred. A correlated API event does not by itself prove that it produced the measured cost.

Proposed operator verification — not an executed test

Validate the anomaly's scope and compare the suspected change with the actual resource and usage increase. Preserve counter-evidence and indicate which causal links remain unconfirmed.

Optimization-recommendation access

Retrieve and contextualize recommendations generated by the underlying optimization services.

F06Preview

Retrieve and filter source-service optimization recommendations

The agent summarizes and contextualizes recommendations produced by those underlying services. It can filter and rank candidates and present current versus proposed configuration and implementation guidance. It does not generate its own independent optimization analysis or perform the resource change.

Input

Permitted Cost Optimization Hub and Compute Optimizer recommendation data, filtered by account, region, service, action type, effort or estimated savings.

Output and interpretation

A shortlist of source recommendations with estimated savings, implementation considerations and source context. Rightsizing, idle-resource and commitment items are recommendation categories, not separate agent optimization engines.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Ask for a specific recommendation scope and the original recommendation identifiers. Inspect source-service enrollment, data availability and permissions when expected items are missing.

Limitations and effects

Savings are estimates, not realized reductions. Alternative recommendations may overlap; summing them can double-count benefits. Performance, resilience and licensing constraints require owner review.

Proposed operator verification — not an executed test

Open the source recommendation, check its freshness and assumptions, identify mutually exclusive alternatives, and obtain workload-owner evidence before raising a change.

Official documentation: Optimization recommendations · Action-specific guardrails and accuracy limits

Reports and task execution

Create reviewable artifacts and manage discrete asynchronous work.

F07Preview

Generate and revise cost-report artifacts

The agent constructs a report with narrative, tables and charts from the retrieved cost or anomaly data. HTML is the documented default, with PDF and editable PowerPoint outputs also supported. A later request can revise an artifact; presentation formatting does not increase the evidential strength of its numbers.

Input

A defined report scope, source data, audience, layout instructions and optionally a reviewed template or organization context.

Output and interpretation

A downloadable artifact associated with its originating task or conversation.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Specify the period, metric, dimensions, required reconciliation table and output format. Inspect the resulting file in Artifacts and its source task before distributing it.

Limitations and effects

Charts can omit dimensions, mislabel periods or represent incomplete data. A professional-looking artifact is not an independently validated financial record.

Proposed operator verification — not an executed test

Reconcile every headline total, verify axes and units, and show the query scope and data cutoff in the report. Keep estimated savings and forecasts visibly separate from actuals.

Official documentation: Custom cost reporting · Web application and feedback · Action-specific guardrails and accuracy limits
F08Preview

Execute and inspect an asynchronous task

The service runs the task through its task queue while the conversation can continue. Task details expose instructions, activities, artifacts and state. Ordinary Chat requests remain conversational unless task creation is requested; an automation is the reusable trigger, not the individual run.

Input

Explicit instructions to create a task, or a scheduled/event automation that instantiates one.

Output and interpretation

A task record with execution activity, status and any artifacts or publishing results.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Ask Chat to create a task or use Tasks → Create tasks. Inspect the task detail page and any pending approvals; cancel a running task there when required.

Limitations and effects

Cancelling a task does not disable future scheduled runs. Deleting an automation does not delete prior task records. A finished task can still contain incomplete analysis that needs review.

Proposed operator verification — not an executed test

Trace one report or published message back to its task instructions and activity. Confirm that the task's time range was resolved as intended rather than carrying a stale interval from an earlier run.

Official documentation: Task management · Web application and feedback · Data protection and deletion lifecycle

External publishing

Treat Jira and Slack actions as destination-specific writes with different approval behavior.

F09Preview

Create a Jira issue in a connected project

The agent creates an issue in the selected project. Interactive and on-demand task creation requires approval; scheduled or event-based automation can pre-authorize this action at setup. Project routing does not include changing an assignee, priority or workflow status.

Input

A connected Jira Cloud project and proposed summary/description containing an anomaly or recommendation.

Output and interpretation

A Jira issue and link to the originating agent task. Assignment and priority come from Jira project configuration rather than an owner-map command to the agent.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Register the Jira integration, add the agent's project connection, then request the issue and inspect project, summary and description before approving an interactive action.

Limitations and effects

Jira Cloud only in the cited guidance. The agent cannot update issue fields, delete issues or administer workflows. A recommendation written into a ticket remains an unimplemented proposal.

Proposed operator verification — not an executed test

Use a test project to verify destination, default assignment and evidence links. Reject any claim that a named engineer was assigned unless Jira itself records that action.

Official documentation: Jira connection and supported actions · Action-specific guardrails and accuracy limits · Task management
F10Preview

Read Jira issue state and append follow-up comments

The agent can read issue metadata to follow disposition and append a comment with updated analysis. Comment addition follows the same interactive versus pre-authorized automation distinction as issue creation. Reading a status is not authority to transition it.

Input

An accessible issue in a connected project, such as an issue created for a previous anomaly or recommendation.

Output and interpretation

Retrieved issue metadata or a new comment linked to the ongoing task context.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Specify the exact issue key and the proposed comment content. Inspect the approval for interactive or on-demand writes and the task history for automated writes.

Limitations and effects

The documented integration describes follow-up comments on issues the agent previously created. Do not generalize it into unrestricted project editing or automatic remediation-state transitions.

Proposed operator verification — not an executed test

Confirm the issue key, project connection and previous task relationship. Compare the actual Jira comment with the approved or pre-authorized content and avoid duplicate updates.

Official documentation: Jira connection and supported actions · Action-specific guardrails and accuracy limits
F11Preview

Post results and artifacts to a connected Slack channel

The agent posts messages and artifacts to connected channels. During preview this is one-way: it does not read messages, accept commands, respond to mentions or continue a thread. Posting does not request per-message approval, even from an interactive task.

Input

An agent-level Slack channel connection and the result or supported artifact to publish.

Output and interpretation

A Slack message or uploaded artifact with source context and task linkage.

Invocation, limitations and proposed verification

Where to invoke / prerequisite

Register the workspace integration, add the app to the intended channel, create that channel's agent connection, then explicitly select the destination in the task or automation.

Limitations and effects

The agent cannot edit/delete the post or manage channel membership. A connected channel can expose cost data to a broader audience; a pending Jira approval does not hold back a separate Slack post.

Proposed operator verification — not an executed test

Test with non-sensitive content and verify audience, channel ID, artifact and source link. Restrict connections before creating unattended publishing workflows.

Configuration mechanisms

How to enable or constrain the functions above. Configuration details are not counted as separate use cases. Recommended verification exercises have not been run against an AWS account.

FM1

Configure source access, operator access and publishing connections separately

The agent role reads the configured AWS data and supports required integrations; the operator role supports the web application. A user's access to the web application does not by itself prove the agent can query every desired billing source. OAuth registration and per-agent destination connections are additional boundaries.

Configuration sequence

  1. In the creation wizard, choose or create the agent role and operator role. The official setup guide defines separate policies; both service roles trust finops-agent.amazonaws.com.
  2. Enable and authorize the billing/optimization sources required for the intended functions. Verify Cost Explorer, Cost Anomaly Detection and source recommendation availability independently.
  3. Sign in as the intended operator and test a minimal permitted query. Record the account scope and sources that are unavailable.
  4. Register Jira or Slack at account level only when needed, then create agent-level connections for specific projects or channels. Do not infer a working destination from a registered integration alone.

Lifecycle and update behavior

Each agent has isolated content and task data, although account-level integrations can be reused. Disconnecting a destination and deleting the agent are separate operations.

Proposed verification — not an executed test

Proposed check: verify one permitted query and one intentionally out-of-scope query; inspect actual role/tool errors. Validate a non-sensitive publishing action in a dedicated destination.

Official documentation: Creating an agent · Setup and role policies · Jira connection and supported actions · One-way Slack publishing · Data protection and deletion lifecycle
FM2

Use organization context and retained preferences without changing source facts

Context files supply account-owner mappings, category definitions and report rules. The agent reads these files but cannot edit them in conversation. Memory can retain preferences and corrections across sessions; long-conversation summarization is a separate context-management mechanism. Neither modifies Cost Explorer or proves that a previous causal conclusion was correct.

Configuration sequence

  1. Upload a small reviewed account-owner mapping in Context files, with effective date and an explicit unknown-owner policy. Do not include sensitive personal data; users with access to the agent can see its context.
  2. Ask Chat to remember a specific reporting preference or correction. Keep a record of the intended rule outside the agent as well.
  3. Run a new session and inspect whether the requested attribution and report convention are applied. Check contradictory or stale mappings before assuming memory is authoritative.
  4. Use Context files to soft-delete or restore uploaded content; ask Chat to forget a memory item. Do not expect deleting a context file to erase conversations or task records.

Lifecycle and update behavior

Context files and memory are per-agent. Conversations and task records cannot be individually deleted during the documented preview; deleting an automation stops future runs but preserves prior tasks. Removing all interaction data requires deleting the agent after disconnecting integrations.

Proposed verification — not an executed test

Proposed check: include one mapped and one unmapped account, then correct the mapping and test a new session. Verify both attribution and totals; an owner label must not change the measured amount.

Official documentation: Context files and memory · Data protection and deletion lifecycle · Web application and feedback
FM3

Configure recurring and anomaly-event automations

An automation stores the trigger and instructions and creates a new task for each matching occurrence. A scheduled report and an anomaly investigation use the same task facility but different trigger semantics. The current event mechanism is cost-anomaly-specific, not a general subscription to any AWS event.

Configuration sequence

  1. First execute the intended instructions as an on-demand task and validate its scope, incomplete-data behavior and output.
  2. For a recurring workflow, define the schedule in Chat and inspect the resulting automation's schedule, enabled state and resolved time basis in Automations.
  3. For an anomaly workflow, select an existing Cost Anomaly Detection monitor, qualifying conditions and the required response. The service provisions an EventBridge managed rule; its role must allow the documented event configuration.
  4. Connect the intended Slack channel before using the documented anomaly-to-Slack workflow. Review any automatic Jira creation as pre-authorization, not as a future approval prompt.
  5. Inspect last-triggered time, task history and destination delivery. Disable the automation to stop future runs; cancel already-running tasks separately.

Lifecycle and update behavior

A trigger arriving does not guarantee a complete analysis or successful publication. Expired OAuth credentials, missing sources and invalid destinations are task failures that require ownership.

Proposed verification — not an executed test

Proposed check: use a controlled permitted event or a prepared event record; verify monitor matching and task creation. Do not manufacture a billing anomaly and claim the live detector was tested.

Official documentation: Task management · Event-triggered anomaly investigation · Action-specific guardrails and accuracy limits · One-way Slack publishing
FM4

Apply action-specific approval and data-location controls

Read-only queries and report generation do not require approval. Jira creation/comments require approval for interactive and on-demand work, but not when pre-authorized in a schedule or event automation. Slack posting requires no per-message approval. These controls do not grant permission to resize infrastructure or purchase commitments.

Configuration sequence

  1. Before deployment, evaluate us-east-1 storage and US-geography inference against the organization's requirements; do not confuse workload region with agent-data location.
  2. Inventory each external write in the task: issue creation, comment addition and Slack posting. Record the destination and whether setup pre-authorizes unattended execution.
  3. Restrict connections to approved destinations. Keep an analysis-only task separate from a publishing task during initial validation.
  4. Review task history for actual tool calls and publish results. Treat a generated draft, an approved action and a delivered external message as distinct states.

Lifecycle and update behavior

Changing automation instructions or destination connections can change future effects. Cancelling or deleting one object does not undo a message already posted or an issue already created.

Proposed verification — not an executed test

Proposed check: reject a proposed Jira action and confirm no issue/comment appears; test Slack separately with non-sensitive content because it does not wait for the same gate.

Operational procedures

Proposed procedures for a specific engineering decision. They compose named functions and include stop conditions. They are not stories of successful customer deployments.

FU1Proposed procedure

Explain a cost increase without inventing a cause

Reconcile a selected cost delta and distinguish measured contributors from unconfirmed explanations.

Use when

An application owner reports higher spend or a detector identifies an anomaly in a known account/service scope.

Do not use this to claim

Inferring a deployment's effect from temporal coincidence, comparing unequal billing scopes, or assigning a usage/rate split when the underlying fields are missing.

Uses: F01, F04, F05, F07

Required inputs

  • Baseline and comparison intervals of known length; same cost metric, currency, accounts and filters.
  • Totals plus a breakdown sufficient to reconcile the change; quantities and effective rates when a usage/rate explanation is required.
  • Anomaly ID and monitor if applicable; deployment/resource events as optional causal evidence.
  • Data cutoff, known credits/adjustments and an owner for unexplained residuals.

Execution and decision points

  1. Cost engineerLock the comparison contract

    Write the two periods and scope before querying. If the reported dashboard used a different metric or filter, reproduce that view first.

  2. Agent and engineerReconcile the difference

    Retrieve totals and contributors; recalculate absolute and percentage changes. Require the dimension contributions plus residual to equal the total difference.

  3. EngineerSeparate arithmetic from causality

    Where quantity and rate exist, explain the chosen decomposition convention. Where they do not, label the driver unresolved. Do not use a smooth chart as evidence.

  4. Agent and ownerTest a candidate operational cause

    Correlate any CloudTrail or deployment event with the specific resource and changed usage. Seek a counterexample, such as increased cost preceding the change.

  5. Cost engineerPublish a bounded conclusion

    Report reconciled totals, supported contributors, uncertain causes and next required evidence. Review the artifact before choosing a publishing action.

Acceptance evidence

The total delta reconciles to explained components plus residual, and every causal claim points to more than temporal coincidence. The report states the exact scope and cutoff.

Stop / escalate

Stop comparison if period, currency or cost basis cannot be matched. Stop driver attribution if the supporting quantity, rate or resource evidence is absent.

Example instruction and demonstration runbook

Example instruction; adapt identifiers and authorization to the actual environment.

Compare <baseline> and <current> using <metric/currency/account filters>. Reconcile the absolute delta by <dimensions> and retain any residual. Distinguish quantity, rate and mix only where source data supports the split. Treat correlated events as hypotheses. Do not publish externally or modify resources.

FU2Proposed procedure

Turn one optimization recommendation into reviewable engineering work

Select a feasible source recommendation and create a bounded work item without claiming that savings are realized or that infrastructure was changed.

Use when

Cost Optimization Hub or Compute Optimizer has a current recommendation for a resource with an accountable owner.

Do not use this to claim

Summing mutually exclusive alternatives, applying rightsizing without workload evidence, or expecting an owner-map file to set Jira assignee fields.

Uses: F06, F09, F10

Required inputs

  • Original recommendation ID, source service, observation period and current/proposed configuration.
  • Estimated savings and assumptions; alternatives affecting the same resource or commitment.
  • Performance/resilience constraints and recent workload demand information from the resource owner.
  • A connected Jira project and explicit interactive approval or reviewed automation authorization.

Execution and decision points

  1. Cost engineerRetrieve the original recommendation

    Open the source record, confirm freshness and identify overlapping alternatives before creating a savings total.

  2. Workload ownerDecide whether the change is feasible

    Review peaks, latency, redundancy, compatibility and rollback. Reject or defer if source utilization is not representative of the intended workload.

  3. Agent and operatorPrepare the issue

    Include resource identity, source recommendation, estimate assumptions, verification plan and owner contact in the description. Select the connected project; do not claim to set assignee or priority.

  4. OperatorApprove and verify publication

    Approve the interactive issue creation, then inspect the actual Jira issue and its defaults. Keep deployment approval outside this action.

  5. Cost engineerMeasure after a separate approved change

    Once engineering deploys a change, compare a representative matched period and document workload differences. Read issue state or add a follow-up comment; do not imply the agent transitioned the workflow.

Acceptance evidence

The issue points to a current source recommendation and records feasibility, implementation and measurement requirements. Estimated and realized savings remain separate fields.

Stop / escalate

Do not create an implementation commitment when the owner, source assumptions or rollback are unknown. Do not publish to an unapproved project or audience.

Example instruction and demonstration runbook

Example instruction; adapt identifiers and authorization to the actual environment.

Retrieve recommendation <id> and summarize its source, current/proposed configuration, estimate assumptions and overlapping alternatives. Draft a Jira issue in <connected project> with an independent verification plan. Request approval before creating it. Do not change resources or issue fields.

Documentation qualifications

Optimization recommendations are attributed to their source services; this guide does not present retrieval as an independent agent optimization engine.
The interaction guide's general approval wording is qualified by the action-specific guardrail page: Jira automations are pre-authorized, and Slack posting has no per-message approval.
No undocumented general event subscription, Slack conversation listener, Jira workflow editor, infrastructure mutator or commitment-purchase action is inferred from the available integrations.
The worked example tests reconciliation logic only. There is no live billing-data reconciliation, agent-run benchmark or measured savings result in this deliverable.
