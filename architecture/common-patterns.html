01 / Decision brief

Common work contracts, evidence, authorization and verification patterns across four products.

The four agents do different jobs and expose different execution surfaces. A useful common architecture does not hide those differences. It defines what a task means, where evidence comes from, which effects are permitted, who owns the decision and how the result is verified.

The running tabletop begins with a checkout incident and ends with a reviewed implementation and independent verification. Security and cost assessments are conditional branches, not mandatory calls to every agent. The connecting artifact is an existing incident, issue or change record. Credentials and approvals are deliberately not passed along with it.

Recommended starting decision

Standardize scope, evidence, ownership and acceptance first. Automate a handoff only after its specialist boundaries work reliably without automation.

Audience
Platform architects, engineering leads, security governance and service owners
Availability
Team-level synthesis of documented mechanisms. Not an AWS shared runtime, unified permission model or implemented multi-agent orchestrator.

02 / Running example

An incident-to-change handoff across specialist boundaries

Illustrative scenario, not an observed customer result or an executed demonstration.

Trigger
An operator has evidence of a checkout failure and a bounded implementation task.
Scope
One workload, named owners, selected specialist tasks and explicit allowed effects.
Deliverable
A chain of evidence-linked work items whose results and authorization decisions can be reconstructed.
Not done

Several agents have generated compatible-looking summaries, but there is no independent verification or accountable owner.

Done means

Each specialist's result is accepted against its contract, every effect is locally authorized, and the final outcome is independently checked.

03 / Use-case execution sequence

Steps, responsibility, review records and acceptance

Each step separates documented product mechanisms from proposed team steps. Responsible roles, evidence-retention records, gates and fallbacks are not native agent assurances.

01

Choose a specialist and write the work contract

Related capabilities: P01 · P04

Operation and evidence context

Start with the evidence and outcome required. DevOps Agent supports operational investigations; Kiro supports reviewable code work; Security Agent supports authorized application assessments; FinOps Agent supports cost analysis. Calling every agent on every task adds complexity without necessarily adding useful evidence.

The proposed common contract records the workload, owner, task, allowed effects, exclusions, completion checks and stop responsibility. A product workspace or prompt is not proof that access is enforced. Test the actual IAM, repository and integration boundaries used by the chosen specialist.

Required input and scope

Review record to retain (proposed)
A bounded work contract with exact accounts, repositories or targets.
Independent acceptance gate
The owner can identify the result needed and the effects that are not permitted.
Failure / fallback
Use a manual specialist workflow until scope and ownership are unambiguous.

02

Assemble evidence with provenance

Related capabilities: P02 · P03

Operation and evidence context

Collect the source references needed to evaluate the task: incident window, deployed revision, repository branch, assessment target or cost-query basis. Preserve timestamps, scope and known gaps so the next reviewer can reproduce a material observation rather than trusting a summary.

Steering, skills, instructions and memory can guide work, but they are not authorization grants or substitutes for current evidence. Treat external documents, tool outputs and repository content as potentially untrusted input. Separate what the agent is told from what its identity is allowed to do.

Source-system custodian
Required input and scope
Relevant source records and clearly labeled instructions or organizational context.
Review record to retain (proposed)
An evidence packet with provenance, freshness and unresolved questions.
Independent acceptance gate
A material claim can be traced to an accessible source in the correct scope.
Failure / fallback
Mark the result inconclusive when the source record is absent, stale or contradictory.

03

Classify the effect before selecting the control

Related capabilities: P05 · P06 · P12

Operation and evidence context

Reading telemetry, editing a branch, sending a request to an application and posting a report are different effects. Their approval requirements should not be flattened into a single idea of human oversight. In particular, an isolated worker can still act against a live target, and an analytical task can still publish sensitive information externally.

Evaluate availability, entitlement, Region, data handling and target safety for the exact feature. The GA label of one product path does not apply to its preview features. Keep the action-control matrix explicit enough that operators can tell what requires approval and what may run automatically once configured.

Responsible role (proposed)
Change approver
Required input and scope
Intended effect, target, product surface and data-location requirements.
Review record to retain (proposed)
An effect-specific authorization and isolation decision.
Independent acceptance gate
Worker controls, target controls and output audience are all understood.
Failure / fallback
Reduce to a read-only or draft-only path when the required authority is not available.

04

Run a bounded job with a stop owner

Related capabilities: P07 · P09

Operation and evidence context

A documented API, integration or remote protocol can be an adapter between systems; it does not establish a universal agent-to-agent transaction. Choose only the interfaces needed for the task and retain each product's access model. Manual handoff is a valid first implementation.

Bound the job's time, spend, retries and concurrency where the product provides controls, and add team procedures where it does not. A recurring schedule needs a recipient, duplicate-work policy and stop owner. Record partial and failed outcomes rather than treating lack of a response as success.

Responsible role (proposed)
Execution owner
Required input and scope
Authorized task, explicit adapter and operational limits.
Review record to retain (proposed)
A run record with status, owner, effect log and stop or retry decision.
Independent acceptance gate
Operators can interrupt work and identify incomplete results.
Failure / fallback
Use a prepared, labeled example for presentations and the established engineering process for real work.

05

Transfer a reviewable artifact—not inherited privileges

Related capabilities: P08 · P11

Operation and evidence context

For an incident-to-fix handoff, the next specialist receives the affected repository, observed failure, evidence references and regression-test expectations. It does not receive production credentials or a blanket instruction to implement every mitigation. A security finding or cost recommendation follows the same artifact principle.

Keep work-item IDs, source revisions and reviewer decisions stable across systems of record. The receiving specialist establishes its own authorized access and acceptance criteria. That preserves accountability even when the handoff is automated later.

Responsible role (proposed)
Receiving specialist and reviewer
Required input and scope
Accepted specialist output with scope, evidence and unresolved limitations.
Review record to retain (proposed)
A linked implementation, assessment or optimization task with a new accountable owner.
Independent acceptance gate
The recipient can evaluate the result without inheriting the sender's approval authority.
Failure / fallback
Reject an incomplete handoff and request missing evidence instead of filling gaps with assumptions.

06

Verify independently before widening the system

Related capabilities: P10 · P11 · P12

Operation and evidence context

Verification must be independent of the claim being accepted. Compare an incident conclusion with telemetry, a code change with meaningful tests and review, a repaired finding with revalidation, and a cost recommendation with a consistent post-change measurement. Agent agreement alone is not independent verification.

Pilot one workflow before building a broad orchestrator. Measure acceptance, rework, boundary failures, time spent reviewing and the quality of retained evidence. Expand only where the operating process is understood and the chosen interfaces and feature availability support it.

Responsible role (proposed)
Independent reviewer
Required input and scope
Specialist output and an independent acceptance method.
Review record to retain (proposed)
An owner-approved outcome and evidence-based expansion decision.
Independent acceptance gate
The final decision can be reconstructed from sources, controls and verification records.
Failure / fallback
Keep the workflow manual or narrow its scope when evidence or control reliability is inadequate.

Bounded asynchronous work and stop responsibility

Proposed architecture pattern · Different mechanisms · Team architecture pattern

Proposed architecture pattern

Invocation and scope

Job record with lifecycle transitions, time/cost budget, and stop/retry decisions.

Known limits and effects

Client timeout is not proof that server work stopped. Product quotas, elapsed time, billable work, and spending caps are different concepts.
