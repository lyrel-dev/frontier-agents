Aperture: consolidated architecture, implementation and evidence

Documentation baseline C2 · 21 October 2026
A consolidated reference for the comparative research, Aperture design and releases, LiteLLM source review, correction, and restricted integration candidate. This is a documentation consolidation, not a new software release.

The product goal remains to make enterprise AI services easy to adopt, safe to change and understandable to operate. The common object is a versioned AI Service Contract. Success is a user completing a governed task with accurate evidence, not the number of screens, adapters or test assertions.

Current position: Aperture Release 14 is the latest delivered local persistent reference. Its model execution is synthetic. The LiteLLM integration kit is separate candidate code with an unimplemented durable Authority binding. The duration correction remains an unmerged draft. No document in this set establishes production approval.

3. Product goal and bounded pilot

Aperture should expose a coherent service journey: describe intent, validate constraints, obtain independent approval, activate the approved contract, execute within authority, and explain the resulting evidence. The same conceptual resources should be visible in the UI, automation interfaces, request evidence and financial attribution. The viewing filter is a convenience; it is never an authorization grant.

The candidate pilot remains internal, non-sensitive text brief drafting with mandatory human review. No retrieval, tool side effects or automatic publication are part of its initial contract. Actual owners, provider/deployment, processing region, financial allowance, participant cohort and organizational approvals have not been supplied. Those are explicit open inputs, not values to fill with synthetic demo personas. Pilot protocol, research-workbench guide

The principal user tasks remain service onboarding to a first observed response, diagnosis of a denied/failed/unknown request, and review through verified activation of a change. Financial investigation crosses those tasks. A test receipt demonstrates some behavior of an artifact; it does not show that representative users understand that behavior. The qualification workbench records such evidence but has not itself generated participant acceptance.

The next UX work should simplify the service workspace and decision summaries only where user observations justify it. Preserve the common change grammar and progressive disclosure. Show the conclusion, responsible owner and safe next step first, with exact differences and technical evidence available underneath. Do not remove an independent decision merely to shorten a journey.

4. Architecture: current reference versus proposed destination

The target design separates Control API, Control Worker, Execution Kernel and Admission Service roles. It places service contracts, policy compilation, governed releases and financial authority under explicit ownership. It originally proposed a small Go kernel with build-time adapters and PostgreSQL/RLS defense in depth. These remain proposals, not descriptions of the current R14 distribution. Architecture, AP-ADR-003, AP-ADR-004

The actual R14 reference is a Python application with a single SQLite store and an exclusive process owner. It offers a standard-library local HTTP path and an optional ASGI path. Execution, observation and delivery workers use the same local authority/store. Separating modules does not turn them into independent deployable services or prove multi-node coordination. The model adapter is deterministic and accepts execution metadata, not a live user prompt sent to a model. R14 implementation, source

The separate candidate’s path is:

Verified host subject
  -> host Authority.begin(contract, request): authorize / replay / reserve
  -> host Authority.claim(permit): recheck / consume one dispatch right
  -> bounded candidate transport: one HTTPS POST to a qualified LiteLLM gateway
  -> validate response and usage evidence
  -> host Authority.record(permit, evidence): persist or recover the receipt

The three Authority operations are interfaces. There is no delivered wire from Aperture R14 to this candidate. The test-only MemoryAuthority does not supply the missing durable binding. A future implementation may reuse R14 concepts, but must explicitly map transactions, identities, replay, revocation, price revisions and unknown exposure. Candidate interface, integration guide

Runtime-language disposition. Preserve AP-ADR-004 as its original proposal and mark it for reconsideration alongside RV-02. The next increment should qualify reused LiteLLM execution machinery before selecting a replacement runtime. Neither an automatic Go rewrite nor treating the Python candidate as an accepted architecture decision is warranted. This changes the immediate qualification sequence without rewriting historical decision text.

6. Identity, tenancy and authority

In server mode, the browser does not select its effective role. Current server-side membership defines tenant/workspace visibility and command authority. A workload credential is a separately approved, single-service authority; revoking a creator’s human session does not automatically revoke every independently approved workload. Reads, exports, commands and eligible replay require current scope rather than trusting an earlier cached UI state. Identity guide, current security source

Optional federation uses authorization-code sign-in with PKCE, signed token validation and explicit issuer/subject bindings. It does not link identities by matching email or automatically accept provider groups as application grants. Binding and policy revisions participate in authority freshness. Recent authentication before a sensitive action is not a claim of MFA assurance. Reverification does not automatically resubmit the action or resolve an unknown command acknowledgement. Federation source, deployment settings

The server uses scoped role domains rather than treating all reviewers as financial approvers. Tenant-budget authority requires tenant-wide financial authority. Technical case triage and notification recovery have different eligible roles from financial case/delivery recovery. Read access does not imply resend, settlement or approval permission. The current implementation and tests, not merely disabled controls, define those boundaries. R14 guide, API

Administrative tenant/workspace organization is distinct from physical isolation. A synthetic tenant fixture is not a dedicated deployment. PostgreSQL row security, sovereign cells, multi-account operation, production support-access controls and organizational provisioning remain target decisions. The new registry leaves their ADR status Proposed and requires independent evidence before any isolation claim. AP-ADR-002, AP-ADR-007, AP-ADR-008

7. One change grammar, distinct states

The user-facing progression is Draft → Validate → Review → Approve → Activate → Observe. Those words describe distinct events. An approved change can still be stale, fail activation or lack runtime health evidence. A local content fingerprint binds what was reviewed; it is not a cryptographic signature, independent attestation or immutable external audit.

Object / fact Current reference meaning Do not infer
Service Draft, Active or Paused An active service has a successful request or a healthy provider
Change Awaiting review, Approved, Activated or Withdrawn Approval is activation; activation is a qualified rollout
Review content Scoped resource, base revision, before/after proposal, author and rationale are bound Changing the reason preserves the old approval
Observation Request or operational evidence describes an actual recorded state A UI status badge proves execution or delivery
Local operator reference Attestation to an external reviewed record for installation/egress work Authenticated two-person approval or a digital signature

The R14 schema uses Activated. Earlier browser editions may retain Released as a legacy serialized value. Consolidated prose uses Activated for the user concept, but this package performs no data conversion. Historical values are interpreted with their own release contract. The service-change flow rechecks current revision and authority at activation. Restrictive actions such as pause or revoke do not authorize a later restoration. Current installation operations and webhook route plans are trusted local-operator workflows; they must not be presented as the same independently authenticated review mechanism used for service/workload changes. 8. Execution, uncertainty and cancellation

A logical request intent, durable dispatch record, execution attempt and receipt are different identifiers and states. The local reference can queue synthetic work transactionally with its reservation. Before dispatch, current authority is rechecked. Once durable dispatch intent exists, a crash or uncertain outcome must not become a fresh automatic execution. Persistent core guide, current domain implementation

The request state set includes Queued, Dispatching, Completed, Unknown, Reconciled, Not dispatched, Declined and Denied. Explicit pre-dispatch cancellation competes with dispatch inside the database transaction. It does not introduce a fictitious successful provider cancellation after dispatch. The cancellation reason and closed job explain the outcome; consumers should use the implemented schema rather than invent a new Cancelled inference state. Schema, operations

Closing a tab or an inspector does not cancel work. Repeating an eligible command after losing its acknowledgement retrieves the same committed result under its logical key; current identity still applies. A reconciliation observation can establish liability without proving that a model response was received or delivered to the end user. The asynchronous metadata API does not measure end-user response delivery.

The candidate has a separate evidence vocabulary, including Response, Truncated and Unknown. Do not map Response directly to every R14 completion/delivery fact. A future host adapter must explicitly map observed usage, truncated output, failed transport, uncertain dispatch and durable receipt recovery into the authoritative state model. Candidate contract

9. Financial semantics and optimization

Rate allowance, spending reservation, accrued liability and provider billing are separate contracts. The local reference tracks tenant-level financial authority with integer micro-units, held exposure and journal adjustments. Pending/unknown exposure reduces available allowance. A known request-total settlement does not invent missing attempt-level attribution. An acknowledged overrun records liability and restricts further admission; it does not discard the excess to keep a dashboard below budget. Current finance schema, domain implementation

For explaining available authority, use available = authorized allowance − accrued liability − held exposure, subject to the implementation’s blocked state and admission rules. This is a local admission/accounting relationship, not proof that a provider invoice can never exceed a configured amount. Unknown is a distinct state, never shorthand for zero. A counter TTL expiring or a queue becoming empty does not establish that remote liability disappeared.

The candidate checks that the external permit binds the contract/request and carries a positive sufficient reservation. It does not calculate a qualified provider worst-case bound from text bytes. The host must establish token counting, pricing revision, output limits, fixed fees, allowed ancillary work and settlement behavior. Usage reported in a response is metering evidence, not an invoice. Candidate authority requirements

The reviewed LiteLLM source has genuine pre-call reservations, not just asynchronous reporting. It also has estimate-coverage exclusions, configurable failure behavior, throttling exceptions and terminal-path/lease qualifications. Enabling a strict flag is not evidence of universal per-request financial containment. Use LiteLLM controls as qualified implementation mechanisms or defense in depth; do not assume they implement Aperture’s intended durable unknown-liability contract. Pinned review, RV-03

Optimization remains advisory until quality and workload evidence exist. Compare input and output cost on the same workload within approved capability, privacy and context constraints. Show exclusions and uncertainty. Synthetic latency/quality scores and assumed acceptance rates are planning inputs. Cost per accepted outcome requires a defined outcome and actual observations; cheaper output-token pricing alone is not demonstrated savings. Innovation guide, AP-ADR-020, AP-ADR-038

11. Durable signals and governed delivery

The server-side observer evaluates three fixed rules on its own schedule: unknown financial exposure aged at least 60 seconds, queued work aged at least 120 seconds, and at least five denied receipts in a workspace within five minutes. Its nominal interval is ten seconds. Those are reference rules, not accepted enterprise response-time commitments or a general user-programmable automation engine. Signals guide, source

Case workflow (Open, Acknowledged, Resolved), observed condition (Active, Clear, Suppressed) and evidence freshness remain independent. Old evidence becomes Unknown rather than implying the source problem cleared. Resolution rechecks the source condition; acknowledging the case does not stop detection. Recurrence preserves history and requires renewed ownership. Detection does not authorize a configuration change or financial settlement.

R14 adds a transactional notification outbox. A trusted operator reviews a workspace/domain receiver, hostname/path and signing-key reference. No destination or external probe is enabled by default. Event creation and outbox enqueue commit together. Delivery is separately signed and attempted against the approved public HTTPS destination, with no caller URL or redirect following. The receiver function is an example, not a deployed service. Delivery guide, receiver example

Delivery states are Pending, Dispatching, Retrying, Accepted, Blocked, Exhausted, Cancelled and Expired. Here Cancelled is a delivery state, distinct from inference cancellation’s schema. A retry cycle is bounded to five attempts within the original 24-hour lifetime. Stable identity and immutable bytes allow receiver deduplication, but duplicate/out-of-order receipt and final non-delivery remain possible.

Accepted means the receiver returned HTTP 2xx. It does not mean a person read the event, a downstream task completed, the case was acknowledged or the source condition was resolved. Preserve the distinction in dashboards and exports. Minimal event metadata still has privacy and retention implications even when prompts, amounts and free-text notes are excluded. Notification source, transport source

Two different egress contracts must remain separate. Notifications target explicitly approved public DNS names on HTTPS 443 and refuse private/IP destinations. The LiteLLM candidate intentionally connects to an explicitly configured numeric gateway address with hostname-verified TLS. This is a qualified internal-gateway use case, not an exception that should weaken webhook destination validation. Candidate transport

12. LiteLLM correction and qualification boundary

The pinned source correction addresses two duration behaviors. Multi-day hour/minute/second reset paths dropped whole elapsed days during rollover. Prefix parsing accepted malformed input such as 1ms as one minute and 1h30m as one hour. The patch preserves day quotient/remainder and requires complete matching. Its scheduler still preserves the legacy invalid-input fallback; it does not provide a new universal fail-closed scheduling API. Code review, patch

For the fixed input 2026-10-21T15:20:30.123456+00:00, the corrected standardized 48h reset is 23 October at 00:00 under the existing clock alignment. That example is not a claim of 48 elapsed hours after the input instant. Standardized schedules, elapsed durations, aliases and calendar-month semantics must stay explicit in operator previews and audits.

No stored values or reset timestamps were migrated. The read-only audit accepts a sanitized projection with caller semantics; it does not connect to a database, repair rows or certify deployments. A clean syntax result does not prove that existing timestamps or financial history are correct. The native runner requires the exact clean PR checkout and a provisioned environment; isolated subsets cannot satisfy it. Audit, native gate

The source review also corrects general architecture claims. Python gateway/backend entrypoints share proxy implementation and startup dependencies; filtered routes do not prove independent control/data-plane failure domains. Effective configuration includes file ownership and blocked conflicting writes. Cache namespaces and a broad endpoint surface are mechanisms to qualify, not implicit tenant isolation or application compatibility. Review amendments, configuration ownership, cache partitioning

The later integration candidate adds no source commit to the fork. It accepts only plain text and stable intent, reconstructs one nonstreaming Chat Completions request, owns model/retry/cache parameters, validates permit bindings and records evidence through the host interface. Real proxy behavior, native package imports, database/Redis interactions, provider compatibility and production finances remain outside its exercised scope. Candidate guide

15. Safe package use and migration

From the extracted consolidation package, enter the unchanged R14 distribution, not the candidate or an archived older package:

cd runtime/aperture-r14
python server.py init
python server.py serve

Initialization creates a new local store and prints generated passwords once. Do not initialize over an existing store or expose the development listener publicly. Use the exact loopback address printed by the server. Opening the HTML directly runs the separate browser demo. Neither workflow enables a webhook destination or real inference by default. Current README

The optional ASGI/federation path uses the distribution’s requirement file and reviewed settings. Production HTTPS requires its specified private socket/TLS edge arrangement; a loopback testing identity provider is not an organizational identity authority. The documentation set has not newly installed dependencies or assessed their present vulnerability status.

Sequential migration policy

Existing persistent stores require the applicable stopped, exact-state plan/apply operations and protected new backup paths.
