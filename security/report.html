01 / Decision brief

Authorized application assessments, findings, remediation proposals and revalidation.

A security assessment is useful when the finding is understandable, the affected application is known, and the team can act on the evidence. An automatically generated severity label is not enough. The application owner needs a reproducible account of the issue, a repair decision and evidence that the repaired deployment no longer exhibits the tested behavior.

The running scenario is an authorized assessment of a staging application with synthetic data and test identities. It follows scope, testing, finding triage, proposed remediation and revalidation. Design and code analysis are presented as complementary preview paths, not as guarantees of complete coverage or interchangeable forms of penetration testing.

Recommended starting decision

Start with one explicitly authorized staging application. Assess the safety of real requests, then connect findings to reviewed repairs and revalidation.

Audience
Application-security engineers, software teams and security platform owners
Availability
On-demand penetration testing: GA. Design review, threat modeling, code review and CI/CD integration are separate preview capabilities.

02 / Running example

Assess and repair an owned staging application

Illustrative scenario, not an observed customer result or an executed demonstration.

Trigger
A team wants evidence about an application change before deciding how to proceed with release.
Scope
Verified targets, written authorization, test accounts, synthetic data, explicit exclusions and a stop owner.
Deliverable
A triaged finding linked to the tested revision, a reviewed remediation proposal and revalidation evidence.
Not done

A generated fix exists, but it has not been reviewed, deployed to the test target or reassessed.

Done means

The authorized test, code review and revalidation records support an owner-approved disposition of the finding.

03 / Use-case execution sequence

Steps, responsibility, review records and acceptance

Each step separates documented product mechanisms from proposed team steps. Responsible roles, evidence-retention records, gates and fallbacks are not native agent assurances.

01

Make authorization and target safety explicit

Related capabilities: C01 · C02 · C04

Operation and evidence context

Define the application, exact target addresses, permitted test window, identities, exclusions and stop authority. Domain verification is a technical prerequisite; it is not permission from every system owner affected by a request. A staging label alone does not prove that payments, emails or other downstream effects are disabled.

Penetration testing sends real requests and can change application state. Use synthetic data and appropriately limited test identities, and understand the configured execution and spend controls. The demo should be possible without touching production or a third party outside the authorization.

Review record to retain (proposed)
An assessment authorization and preflight record.
Independent acceptance gate
The owner has approved the targets and business effects, not merely a hostname.
Failure / fallback
Stop preparation when authority or downstream effects are unclear; use a labeled schematic walkthrough instead.

Give the assessment current application context

Related capabilities: C02 · C03

Operation and evidence context

Use the documented credential and private-connectivity paths rather than pasting secrets into example prompts or reports. Record what was reachable and authenticated. A test that did not reach a protected workflow cannot provide evidence that the workflow is safe.

03

Observe the run and triage the evidence

Related capabilities: C01 · C04 · C05

Operation and evidence context

Monitor the authorized task and inspect findings as evidence about a particular application state. Prioritization should combine the reported impact, reproducibility, affected data or role, and the service owner's business context. Do not equate finding count with assessment quality.

Preserve the path from the observation to the affected revision and identity. A validated exploit path can be valuable, but a clean result is not proof that every vulnerability class or application route has been covered. Escalate uncertain findings for human review rather than turning uncertainty into a release assurance.

Failure / fallback
Pause or stop on unexpected effects and retain an incomplete-run record instead of treating it as a pass.

04

Review a proposed repair as an engineering change

Related capabilities: C06 · C09

Operation and evidence context

With the appropriate repository configuration, a finding can lead to a proposed code repair. That proposal needs normal review for correctness, compatibility and test coverage. A patch that blocks the observed path may still create a regression or leave a related path unresolved.

Track the finding and repair in the team's existing issue system. A Jira handoff is useful only when the audience is appropriate and the ticket links the evidence, affected revision and acceptance test. Do not publish sensitive assessment details to a broader channel simply because an integration is connected.

Responsible role (proposed)
Development owner and code reviewer
Required input and scope
Accepted finding, permitted repository access and a repair owner.
Review record to retain (proposed)
A reviewed PR/MR or repair plan linked to the original finding.
Independent acceptance gate
The proposed change passes independent review and normal delivery controls.
Failure / fallback
Assign a manual repair when repository support, authorization or generated output is inadequate.

05

Deploy to the authorized target and revalidate

Related capabilities: C07 · C08

Operation and evidence context

A code fix is not the same as a repaired deployed application. Record the revision deployed to the authorized test target before requesting revalidation. Compare the result with the original evidence and confirm that the targeted behavior is no longer reproducible under the intended conditions.

Export a point-in-time report that preserves the scope, results and unresolved limitations. Closing the issue is an owner decision supported by assessment evidence, code review and revalidation. None of those artifacts alone is a certificate that the application is secure.

Security operator and application owner
Required input and scope
Reviewed repair deployed to the approved target and linked to the original finding.
Review record to retain (proposed)
Revalidation outcome and point-in-time evidence report.
Independent acceptance gate
The closure decision identifies the tested revision and remaining risks.
Failure / fallback
Keep the finding open or explicitly risk-accepted if revalidation is inconclusive or fails.

06

Add earlier feedback without overstating availability

Related capabilities: C10 · C11 · C12 · C13 · C14 · C15 · C16 · C17 · C18

Operation and evidence context

Design reviews, organizational security requirements and threat models can make assumptions and trust boundaries inspectable before testing a running application. Code review can analyze full repositories or configured change triggers, with provider-specific remediation paths. These are distinct from the GA on-demand penetration-testing baseline.

Treat IDE, S3 differential-scan and CI/CD integrations as separate preview adoption decisions. A promotion gate needs explicit thresholds, timeout behavior and a policy for missing or inconclusive evidence. The team owns that release policy; an unavailable or unfinished scan should not silently become a green gate.

Authorization and evidentiary limits

A generated recommendation, PR, finding or cost report is evidence for a decision. It is not a universal approval to act in another product.

Verify current feature availability, integration permissions and target safety before using a workflow. Preserve unresolved evidence gaps and use the existing team process when a configured path is not available.

These are proposed engineering controls, not a claim of one shared AWS permission model.

The pipeline integration is a post-deployment test, not a pre-merge code scan. It assesses the configured deployed change. A scoped-out result can pass without exercising a new attack surface, and infrastructure errors can be configured fail-open. The documented defaults therefore need explicit review.
