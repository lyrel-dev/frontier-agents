AWS FinOps Agent — platform capabilities and mechanisms

Agent-instance configuration, authorized data retrieval, persistent context, task orchestration, artifacts and external publication. Cost-anomaly investigation is an application of these abilities.

Capability inventory

Instance and data access · F-C01

Agent-instance isolation and role separation

Each agent instance has its own permissions, memory, files, task queue and integrations. Data access and operator access are separately configured.

Platform resources

Agent instance; agent role; operator role.

Supported operations

Create an instance; configure the data and operator roles; associate required integrations.

Boundary

Separate instances do not imply a shared organization-wide memory. Access to the agent can expose its shared context to its users.

Instance and data access · F-C02

Authorized source-data retrieval

The agent queries authorized AWS services for cost data, recommendations and operational-change evidence.

Platform resources

Agent role; Cost Explorer data; recommendation sources; CloudTrail access.

Supported operations

Activate dependencies; grant required API actions; inspect data-source provenance and query filters.

Boundary

Removing a source permission can remove a particular analytical input without disabling all cost inquiry. Retrieved recommendations are not an independent optimization calculation.

Context and retained state · F-C03

Organization-specific reference context

Uploaded files provide account mappings, instructions and reporting conventions that the agent can read during work.

Platform resources

Context file; active or soft-deleted state; workspace visibility.

Supported operations

Upload, delete or restore files through the Context files workspace.

Boundary

The agent cannot modify or delete uploaded context files through conversation. Files are visible to users who can access that agent.

Context and retained state · F-C04

Persistent preferences and corrections

Conversational memory retains preferences, ownership details, corrections and previous task outcomes for subsequent sessions.

Platform resources

Agent-instance memory.

Supported operations

Ask the agent to remember, update or forget a non-sensitive fact or preference.

Boundary

Conversational memory is different from the source files containing similar facts. Do not assume that editing one automatically synchronizes the other.

Context and retained state · F-C05

Bounded conversation-context management

As the context limit approaches, older conversation portions are summarized while recent messages remain in full.

Platform resources

Conversation context; older-message summary; recent messages.

Supported operations

Inspect retained decisions and restate critical constraints when needed.

Boundary

Compaction is not verbatim recall or a guarantee that every detail survives. It is separate from cross-session memory.

Execution, outputs and lifecycle · F-C06

Task queue and automation execution

On-demand, scheduled and event-based tasks run through a shared queue; automations create tasks when their conditions match.

Platform resources

Task; automation; schedule; supported event rule; task history.

Supported operations

Create an on-demand task or automation; inspect queued and completed work; stop future creation by removing the automation.

Boundary

The reviewed preview documents Cost Anomaly Detection events, not an arbitrary general event-processing framework. Existing tasks have a separate lifecycle.

Destination-specific external publication

Execution, outputs and lifecycle · F-C09

Object-specific data lifecycle

Persistent agent data is distinct from the ephemeral session runtime, and deletion or stopping behavior depends on the object type.

Platform resources

Context file; memory; conversation; task; automation; agent instance.

Mechanisms and enablement

Mechanism · F-M01

Source-backed analysis and permission dependencies

The service retrieves source data rather than modifying billing records. Optimization recommendations originate in Cost Optimization Hub and Compute Optimizer. The agent summarizes them; it does not generate the underlying optimization analysis.

Capabilities: F-C01, F-C02, F-C08

  1. 1Agent role and query scope
  2. 2Underlying AWS API results
  3. 3Contextual interpretation
  4. 4Reviewable answer or artifact
Trigger

A request or task requires cost totals, recommendation data or evidence of operational changes.

State and lifecycle

The authorized data sources and filters determine the available evidence. Removing cloudtrail:LookupEvents removes change-event evidence without necessarily preventing basic cost inquiry.

Configuration, controls and proposed verificationEnablement procedure
  1. Configure the agent data role and separate operator role through the supported setup path.
  2. Activate the required upstream cost and recommendation services.
  3. Inspect the actual policy actions and data filters rather than relying on a role name.
Controls and failure boundaries

Reconcile numerical results and validate causal explanations separately. A temporal correlation with a deployment is not sufficient proof of the cost driver.

Independent verification — proposed

Proposed check: reproduce a reported total using identical dates, basis, granularity and filters. Independently verify recommendation provenance and any change evidence. Record unavailable sources rather than filling gaps with assumptions.

Mechanism · F-M02

Reference files, conversational memory and compaction

Uploaded context is operator-maintained; conversational preferences can be remembered, updated or forgotten. Older conversation content is summarized as the context budget fills. These are separate state mechanisms.

Capabilities: F-C03, F-C04, F-C05

  1. 1Uploaded files or stated preferences
  2. 2Persistent instance context
  3. 3Session runtime loading
  4. 4Answer or compacted conversation
Trigger

A session or task uses organizational context, or a conversation approaches its context limit.

State and lifecycle

Persistent files and memory are loaded into a session-isolated ephemeral runtime. Agent instances do not share this state.

Configuration, controls and proposed verificationEnablement procedure
  1. Upload authoritative non-sensitive reference files through the Context files workspace.
  2. Use explicit remember, update or forget requests for conversational preferences.
  3. Test file retrieval and memory recall independently; restate critical constraints when evaluating compacted conversations.
Controls and failure boundaries

All users with agent access can see context files. Updating memory does not establish that an uploaded file or prior conversation was also changed.

Independent verification — proposed

Proposed check: establish a harmless preference, open a new conversation and examine its application. Correct or forget it and repeat. Use a different test for uploaded context so file retrieval is not mistaken for memory recall.

Mechanism · F-M03

Event matching and queued execution

The documented anomaly path connects Cost Anomaly Detection, managed EventBridge rules and task creation. On-demand, scheduled and event-based work shares the task queue.

Capabilities: F-C06

  1. 1Monitor event or schedule
  2. 2Managed rule and automation match
  3. 3Queued task
  4. 4Recorded execution result
Trigger

A configured anomaly event or schedule matches an automation.

State and lifecycle

An automation defines future invocation; each created task has its own execution history. The documented preview event source is Cost Anomaly Detection.

Configuration, controls and proposed verificationEnablement procedure
  1. Configure the anomaly monitor and the agent permissions needed to manage the service's EventBridge rules.
  2. Connect the intended destination and define explicit monitor or threshold conditions.
  3. Inspect the resulting automation and rule; a conversational acknowledgement alone is not proof of registration.
Controls and failure boundaries

IAM ownership and account conditions constrain rule management. Destination publishing may be pre-authorized when the automation is configured.

Independent verification — proposed

Proposed check: trace an authorized test event through rule match, task creation, execution and destination result. Remove or disable the automation and verify that future tasks stop; examine existing tasks separately.

Mechanism · F-M04

Action- and invocation-specific publication approval

Interactive and on-demand Jira issue/comment actions require approval. Scheduled or event-based Jira actions are pre-authorized when the automation is configured. Slack posting does not require an approval prompt, including interactive posting.

Capabilities: F-C07

  1. 1Configured destination
  2. 2Action and invocation type
  3. 3Applicable approval rule
  4. 4External artifact and history
Trigger

The agent creates a Jira issue, adds a Jira comment or posts a Slack message.

State and lifecycle

Task history records results. Automation setup is an authorization decision, not just a timing preference.

Configuration, controls and proposed verificationEnablement procedure
  1. Connect only intended Jira projects and Slack destinations.
  2. Inspect the content and destination for interactive Jira approvals.
  3. For automations, review publishing instructions before enabling recurring or event-based execution.
Controls and failure boundaries

Do not describe the service as approval-gated for all external writes. Prevent sensitive context from being placed into automatically published messages.

Independent verification — proposed

Proposed check: in designated test destinations, inspect an interactive Jira approval, a pre-authorized automation result and a Slack post. Confirm the actual destination and record whether an approval prompt occurred.

Mechanism · F-M05

Data lifecycle and processing boundaries

Context-file deletion is reversible soft deletion. Forget requests change memory. Deleting an automation stops future task creation. In the reviewed preview guidance, individual conversations and task records remain until agent deletion rather than supporting individual deletion.

Capabilities: F-C01, F-C09

  1. 1Identify the object
  2. 2Apply its supported control
  3. 3Check retained versus inactive data
  4. 4Confirm processing boundary
Trigger

An operator changes or removes retained context, an automation or the agent instance.

State and lifecycle

The preview stores agent data in us-east-1; Bedrock inference may run in other US Regions. Persistent storage and ephemeral session execution are different layers.

Configuration, controls and proposed verificationEnablement procedure
  1. Identify whether the intended target is a file, memory, conversation, task, automation or whole instance.
  2. Use the documented workspace or lifecycle control for that object.
  3. Review the current storage and cross-Region inference guidance before making a data-location assertion.
Controls and failure boundaries

Soft deletion is not physical erasure. Stopping future automation is not equivalent to removing existing records or already published external artifacts.

Independent verification — proposed

Proposed check: use non-sensitive test data to distinguish inactive, restored, forgotten and retained records. Do not delete a real agent merely to demonstrate lifecycle behavior.

Optional verification exercise

Verify context, event execution and publication separately

Proposed prepared-result exercise; test data and test destinations only · 8 minute walkthrough budget.

  1. 2 min: Inspect the agent data role and source-query scope.
  2. 2 min: Compare a test memory preference with an uploaded reference file.
  3. 2 min: Trace an anomaly event into an automation task and its result.
  4. 2 min: Identify the publishing approval rule and reconcile the reported numbers.
Acceptance

Separate source-data accuracy, retained context, event execution and publishing authority. No measured savings or proven causality is inferred.
