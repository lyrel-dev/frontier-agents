AWS Security Agent — platform capabilities and mechanisms

Application-scoped assessment configuration, authentication, reusable criteria, execution records and finding lineage. An assessment scenario is not itself a platform capability.

The current documentation identifies AWS Security Agent as part of AWS Continuum. Availability is feature-specific: do not apply penetration-testing availability to every design, code, threat-model or pipeline feature. Verify the selected feature before rollout.

Authentication and execution · S-C04

Authenticated and private target access

Verified domains, network configuration, application credentials and service permissions determine the reachable testing surface.

Mechanisms and enablement

Mechanism · S-M01

Learned authentication navigation

The service captures successful navigation as a skill. Later login sessions in the same run and future runs can apply it rather than repeat discovery.

Capabilities: S-C04, S-C05

  1. 1Provided test credentials
  2. 2Successful login navigation
  3. 3Saved skill file
  4. 4Reuse in later sessions
Trigger

The first successful login session discovers how to navigate the configured application's authentication flow.

State and lifecycle

Disabling Login Optimization preserves the saved skill. Re-enabling permits reuse; the documentation describes adaptation when the login flow changes.

Configuration, controls and proposed verificationEnablement procedure
  1. Add at least one representative test credential to the penetration-test configuration.
  2. Open Additional configuration → Login optimization. The section requires an existing credential.
  3. Confirm the default-enabled toggle or deliberately disable it for a controlled comparison.
Controls and failure boundaries

This learned procedure is scoped to authentication behavior. It is not evidence of general incident learning or model-weight changes.

Independent verification — proposed

Proposed check: compare recorded first-run and later authentication behavior in an authorized staging application. Change the test login flow and inspect successful authentication and the observed role; do not equate faster navigation with broader security coverage.

Mechanism · S-M02

Credential resolution and target reachability

Direct input or supported AWS-native credential strategies supply credentials. For advanced strategies, the service resolves the configured resource, then follows login instructions to apply the result. Secrets Manager, role assumption and Lambda are separate strategies.

Capabilities: S-C01, S-C02, S-C04

  1. 1Authorized target configuration
  2. 2Service access to credential source
  3. 3Application login instructions
  4. 4Authenticated test surface
Trigger

An assessment needs access to an authenticated or privately reachable application surface.

State and lifecycle

The current credential and target configuration determines reachable access. Domain verification and optional private connectivity remain separate configuration records.

Configuration, controls and proposed verificationEnablement procedure
  1. Verify the permitted target and configure private connectivity when required.
  2. Select a supported credential strategy and grant the service only the required source access.
  3. Provide login instructions describing where and how the resolved credential is applied; use test accounts without production access.
Controls and failure boundaries

Credential resolution can succeed while application login fails. A verified domain does not authorize every external system reached by the application.

Independent verification — proposed

Proposed check: record the actual authenticated identity, application role and reachable paths. Exercise a permitted path and confirm an out-of-scope path remains excluded. Do not count an unauthenticated run as authenticated coverage.

Mechanism · S-M03

Requirement-pack evaluation and regeneration

Requirements express applicability and compliance criteria. Enabling a pack supplies criteria for subsequent eligible reviews; the review must be configured for requirement evaluation rather than only vulnerability analysis.

Capabilities: S-C03

  1. 1Reviewed requirement definitions
  2. 2Enabled pack
  3. 3Configured review mode
  4. 4Requirement-level findings
Trigger

A configured review evaluates an enabled requirement pack, or an administrator regenerates requirements from documents.

State and lifecycle

Uploading new source documents regenerates the entire pack and replaces existing requirements, including manually added ones. Prior completed assessments are not retrospectively rewritten.

Configuration, controls and proposed verificationEnablement procedure
  1. Open Security requirements and create or select the required pack.
  2. Review each requirement's applicability and compliance criteria before enabling the pack.
  3. Configure the design or code review to evaluate requirements. Do not upload replacement documents unless replacing the existing pack content is intended.
Controls and failure boundaries

Generated requirements need human review. A framework pack is not an audit result or guarantee of compliance.

Independent verification — proposed

Proposed check: evaluate a known compliant example, a known violation and an explicitly inapplicable example. Check applicability and evidence, not only the number of findings. Keep requirement changes in Git or the governing source system.

Mechanism · S-M04

Targeted revalidation with preserved lineage

The service authenticates using current configuration and repeats the selected findings' validation steps. It does not rediscover vulnerabilities or test unrelated areas.

Capabilities: S-C06, S-C07

  1. 1Original finding
  2. 2Separate revalidation job
  3. 3Repeated validation steps
  4. 4Linked result history
Trigger

An operator selects existing findings after a repair is deployed to the original target environment.

State and lifecycle

The original finding is preserved. The separate job reports Active when reproduced and Resolved when not reproduced during that revalidation, with links between findings and jobs.

Configuration, controls and proposed verificationEnablement procedure
  1. Deploy the repair to the environment used by the original completed test.
  2. Open the run and choose Multiselect findings for revalidation.
  3. Select the relevant findings, choose Revalidate findings, and inspect the new job and history links.
Controls and failure boundaries

A non-reproduction result applies to the selected finding, target and execution conditions. It is not a whole-application assurance statement.

Independent verification — proposed

Proposed check: retain the deployed revision, credential identity, finding identifier and new job identifier. Confirm that the expected target was reached and assess whether any login or environmental failure weakened the result.

Official documentationS06 · Finding revalidation

Optional verification exercise

Inspect learned login behavior and a finding revalidation

Proposed prepared-result exercise; authorized staging evidence only · 8 minute walkthrough budget.

  1. 2 min: Inspect the test target, test credential and Login Optimization setting.
  2. 2 min: Compare first and later successful login behavior.
  3. 2 min: Inspect one original finding and the deployed repair revision.
  4. 2 min: Trace its revalidation job and state the result's scope and limitations.
Acceptance

Distinguish authenticated access, learned login reuse and targeted finding revalidation; none establishes general application security.
