Scope and connectivity · D-C01

Scoped operational workspaces

An Agent Space binds infrastructure access, integrations and operator access to a configured operational context.

Platform resources

Agent Space; resource-investigation role; operator web-app role.

Supported operations

Create a space; associate accounts and integrations; configure the separate roles.

Boundary

Workspace membership does not override the permission policies on connected resources.

Context and behavior · D-C05

Persistent contextual knowledge

Managed and custom memory stores retain synthesized information that an agent can selectively retrieve across sessions.

Platform resources

Memory store; Markdown memory entry; description; immutable versions; active state.

Supported operations

Inspect entries and versions; activate or deactivate stores and entries; maintain custom context; attach stores to custom agents.

Boundary

Context retrieval is not customer-controlled model-weight training. Stored information does not establish that it was used or that a new diagnosis is correct.

Execution and control · D-C08

Constrained custom-agent definitions

A custom-agent definition combines a system prompt with selected tools, skills and attached memory stores.

Platform resources

Custom agent; prompt; tool selection; skill and store attachments.

Supported operations

Mechanisms and enablement

Mechanism · D-M01

Recurring-monitor knowledge production

The monitors store groups recurring cause history by alarm or metric. The documented daily learning process runs when there are investigations within the preceding two weeks; it retains per-investigation evidence.

Capabilities: D-C04, D-C05

  1. 1Completed investigations
  2. 2Managed learning process
  3. 3Per-monitor synthesized entries
  4. 4Later investigation context
Trigger

Recent investigations within the Agent Space.

State and lifecycle

Entries without updates for two weeks are removed; capacity pressure removes the oldest item. This store is bounded operational context, not an incident archive.

Configuration, controls and proposed verificationEnablement procedure
  1. Confirm the Agent Space has completed investigations and inspect the managed learning agent History.
  2. Open Knowledge → Memories and inspect the monitors store and matching entry.
  3. Confirm the store and entry are active; monitor memory is documented as enabled by default.
Controls and failure boundaries

Keep current telemetry authoritative when it contradicts historical patterns. Learning runs and data retention are not a model-training control.

Independent verification — proposed

Proposed check: retain an earlier verified cause, inspect the resulting entry, then examine a later incident with a different cause but similar symptom. Distinguish entry existence, observable retrieval and diagnosis correctness.

Mechanism · D-M02

Corrective-feedback reflections

The documented reflections store records lessons about a missed or incorrect cause. Feedback submission and recurring-monitor synthesis are different production paths.

Capabilities: D-C04, D-C05

  1. 1Completed diagnosis
  2. 2Verified correction
  3. 3Reflection memory
  4. 4Future alarm investigation
Trigger

An operator supplies corrective feedback on a completed investigation.

State and lifecycle

Feedback can be updated; the latest submission replaces prior feedback for that investigation. Do not assume that every downstream state is immediately refreshed.

Configuration, controls and proposed verificationEnablement procedure
  1. Open the completed investigation and choose Add feedback, or provide the correction through Chat.
  2. Record the verdict and actual cause; inspect the relevant memory under Knowledge → Memories.
  3. Treat the separate opt-in to share feedback with AWS as a distinct decision.
Controls and failure boundaries

Use a verified correction, not a convenient hypothesis. AWS sharing requires explicit confirmation; local feedback and external sharing are not the same operation.

Independent verification — proposed

Proposed check: link the correction to the original evidence, inspect the stored lesson, and challenge the next diagnosis using current contradictory evidence. Without visible access evidence, report recall as unverified.

Mechanism · D-M03

Selective retrieval and store attachment

The documented retrieval sequence exposes descriptions before full content. For custom agents, store attachments constrain the accessible collection; new agents start without attachments.

Capabilities: D-C05, D-C08

  1. 1Store descriptions
  2. 2Relevant store selection
  3. 3Entry descriptions
  4. 4Selected full content
Trigger

An agent session needs contextual information relevant to its task.

State and lifecycle

Updates create immutable entry versions. Deactivating a store or entry removes it from active access without deleting it.

Configuration, controls and proposed verificationEnablement procedure
  1. Write specific descriptions stating the store subject and relevant situations.
  2. Edit the custom agent and attach only required stores; inspect the resulting definition.
  3. Use supported controls to deactivate stale entries and examine previous versions.
Controls and failure boundaries

A custom agent can write to attached custom stores; attached managed stores remain read-only. Retrieval internals beyond the documented description-selection process are not asserted.

Independent verification — proposed

Proposed check: compare an agent with and without a non-sensitive test-store attachment. Inspect observable reads and verify the answer independently. A repeated phrase alone does not prove retrieval.

Mechanism · D-M04

Startup instruction injection

The service retrieves applicable AGENTS.md content at startup rather than letting the agent select it by relevance.

Capabilities: D-C06

  1. 1Saved global instructions
  2. 2Agent-specific instructions
  3. 3Startup context
  4. 4Session behavior
Trigger

A new applicable agent session starts.

State and lifecycle

Saved changes apply to new sessions; already-running sessions keep their startup content.

Configuration, controls and proposed verificationEnablement procedure
  1. Open Agents → Managed agents and select the relevant agent.
  2. On Agent definition, edit Global instructions or that agent's own instructions.
  3. Save and start a new session to assess the change.
Controls and failure boundaries

Global changes affect all applicable managed agents. Instructions guide behavior but do not expand or restrict IAM authorization by themselves.

Independent verification — proposed

Proposed check: use a harmless output-format instruction, compare a pre-existing session with a new one, and record the content revision used. Treat compliance as observed behavior, not guaranteed policy enforcement.

Mechanism · D-M05

Description-based skill selection

Skills supply procedural instructions through SKILL.md and optional supporting resources. They are selected on demand rather than unconditionally injected like standing instructions.

Capabilities: D-C07

  1. 1Task and agent type
  2. 2Skill description
  3. 3Procedure loading
  4. 4Tool-guided work
Trigger

The current task matches a skill description and agent-type scope.

State and lifecycle

Description, procedure and scope are separate configuration fields that should be maintained together.

Configuration, controls and proposed verificationEnablement procedure
  1. Open Knowledge → Skills and add or import the procedure.
  2. Write a description defining when it applies and select the relevant agent types.
  3. Verify available tools separately; a procedure cannot grant missing tool permissions.
Controls and failure boundaries

An enabled skill can remain unused when its description or scope does not match. A skill is not an authorization boundary.

Independent verification — proposed

Proposed check: submit one matching and one nonmatching task. Inspect available invocation evidence for selection instead of inferring it solely from answer wording.

Mechanism · D-M06

Tool association and directed-action authorization

MCP registration, authentication, Agent Space association and selected tools establish availability. Mutating operations additionally require directed-action controls. AWS actions use the configured elevated role and approval scoped to the operation and resource.

Capabilities: D-C02, D-C03, D-C11

  1. 1Registered provider or account
  2. 2Scoped access and tool class
  3. 3Specific approval
  4. 4Attributed execution
Trigger

The agent selects an associated external tool or proposes an eligible AWS-resource mutation.

State and lifecycle

Provider configuration, selected tools, role policies and approvals are different records. Approval is not reusable for a different operation or resource.

Configuration, controls and proposed verificationEnablement procedure
  1. Register and authenticate the provider, associate it with the Agent Space, and select the required tools.
  2. Review tool classifications explicitly. Programmatically registered tools without classification are documented to default to READ_ONLY.
  3. For eligible mutations, enable directed actions and configure the account role or integration; review the exact operation before approval.
Controls and failure boundaries

Misclassifying a mutating server tool as read-only is an operational hazard. Destructive third-party tools are a separate non-invocable class. A network path does not grant application access.

Independent verification — proposed

Proposed check: in an authorized test environment, verify a read, a rejected mutation and one narrowly approved mutation. Retain tool parameters, approval identity and independent resource state before and after.

Mechanism · D-M07

Ephemeral sandbox execution

The platform provides investigation-local computation with preconfigured packages and outbound endpoint rules. This execution surface is separate from directed-action authorization.

Capabilities: D-C10

  1. 1Agent Space configuration
  2. 2Investigation runtime
  3. 3Permitted code and network work
  4. 4Investigation output
Trigger

An investigation uses the explicitly enabled Sandbox capability.

State and lifecycle

The environment is ephemeral and scoped to an investigation; do not use it as a persistent knowledge store.

Configuration, controls and proposed verificationEnablement procedure
  1. Open Capabilities → Sandbox → Configure for the Agent Space.
  2. Opt in and set package requirements and permitted outbound hosts, methods and paths.
  3. Confirm current feature and Region availability before an authorized test investigation.
Controls and failure boundaries

The reviewed preview scope is investigations, not all chat or custom-agent work. Network permissions and workload permissions remain separate controls.

Independent verification — proposed

Proposed check: run a harmless computation, confirm allowed and denied outbound requests, and verify that the output is retained in investigation evidence rather than assumed to persist in the runtime.

Optional verification exercise

Verify contextual recall without accepting a stale diagnosis

Proposed prepared-result exercise; no live execution or runtime guarantee · 8 minute walkthrough budget.

  1. 2 min: Inspect a completed investigation and its verified correction.
  2. 2 min: Inspect the monitor entry or reflection and its current state.
  3. 2 min: Review a later invocation for observable retrieval evidence.
  4. 2 min: Challenge the conclusion with current contradictory telemetry and record unknowns.
Acceptance

Report three separate outcomes: memory exists, memory use is observable or unverified, and diagnosis is independently supported or rejected.
