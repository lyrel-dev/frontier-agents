Capability and use-case format

Standard record fields for the interactive reports and timed presentations.

Full editorial standardAll reports
Engineering publication standard

Use a fixed evidence structure for every feature and workflow

A product capability is a documented mechanism; a use case is a bounded sequence that applies mechanisms to a problem. Keep proposed team controls separate from product behavior. Speaker notes contain details that would reduce slide legibility.

Report mode

Full capability fields, steps, limitations, acceptance evidence and official URLs.

Presentation core

Decision-oriented slides and timeboxed demonstrations; fewer statements on each slide.

Reference appendix

One untimed capability slide per entry, available for technical questions.

1. Capability record — seven fields

#FieldRequired contentPlacement
1Identity & maturityCapability ID, product or surface, feature status and delivery mechanismAlways visible

5Independent acceptanceEvidence or test capable of contradicting the agent resultExpanded record

2. Use-case record — bounded process

StageInformation required
ContextTrigger, target, time window and owner
ScopeAllowed effects, exclusions, client/Region/permission constraints
Action sequenceSteps with inputs, responsible role and cited native mechanism
OutputReviewable artifact and source provenance
DecisionAcceptance condition, reviewer and authorizer
Failure pathMissing evidence, blocked permissions, rollback/stop and fallback

For each execution step, show a proposed responsible role, the required input, operation narrative, reviewable artifact, acceptance gate, fallback and source IDs. Do not imply that crossing products transfers credentials or approvals.

3. Slide selection by information type

LayoutUse it for
Scenario contractOne bounded problem, expected artifact, exclusions and acceptance
Capability matrixOnly related functions; label preview and configured paths
Input → function → artifactOne mechanism, with source dependencies and independent verification
Controls / availabilityExactly which actor can perform which effect and under which conditions
Live demoTimed steps, preflight, source evidence, pass/fail and prepared fallback
Untimed referenceOne slide per capability; full function, setup, record, verification, limits, sources
The 70 core slides remain timed at 128 minutes including 35 minutes of walkthrough demonstrations. The 50 capability-reference slides are untimed and do not change these allocations. Questions and breaks are additional.

4. Neutral wording

AvoidUse
"AI automatically resolves production incidents.""A connected investigation can produce a mitigation proposal. Production changes require the configured execution and approval path."
"Security assurance is end-to-end.""A scoped assessment returns findings; the team reviews fixes and revalidates the authorized target."
"Optimize cloud costs effortlessly.""Reconcile source totals, review optimization recommendations and measure separately approved changes."
"Agents share one permission boundary.""A team can pass evidence between products; permissions and approval controls remain product-specific."

Write claims as observable operations, not performance promises. “Automatic” is appropriate only where a documented trigger actually initiates a task. Unmeasured quality, time-saving or cost-saving claims must not appear as achieved results.

5. Publication checks

Evidence

Every product statement cites an official feature source. Label preview and client/Region limits. Label proposed artifacts, owners, prompts and cross-agent sequences.

Execution and quality

Show permissions and side effects. Include independent checks and fallbacks. Verify timed durations, readable layouts, local links and uncropped content. No untested benefit is represented as measured.

This is a documentation and presentation standard, not a product capability claim. Source evidence is linked within each report.
