# Editorial standard

## Explanatory sequence

Introduce the agent and its resource model before listing functions. Explain integration direction and authorization before describing data use. Explain how knowledge is produced, retained, selected, corrected, and removed before applying it to a use case.

## Prose and headings

Use descriptive sentence-case noun phrases, as in a technical book. Begin a section with the idea and its relationship to the preceding topic. Use procedures and tables where they answer configuration or comparison questions; do not substitute labeled fragments for an explanation. Catalog records are narrated situations, work, and interpretations with reference fields as a supplement.

## Outcomes and implementation relationships

Maintain each operational objective once. Every primary case has a responsible actor, completion criteria and connected narrative. Preserve separate cases when the result, decision or authorization boundary differs. Treat cadence, network route, identity and format as variants when the operational objective remains the same.

Workflow steps identify purpose, responsible actor, required/optional/conditional mechanism, its condition, concrete feature configuration, effect, acceptance evidence and failure handling. Human review is labeled as a team procedure rather than invented native behavior. A feature is a concrete service facility; its mechanism explains a documented process. The guide remains the detailed technical authority.

An implementation profile supplies reusable configuration choices and proposed acceptance exercises. It is not a deployable AWS schema or a claim that products share permissions, runtime or memory. Product-specific publication and mutation controls remain attached to the selected variant after consolidation.

Keep old identifiers and titles as aliases to the maintained successor. A split record offers all relevant successors rather than choosing silently. Alias data is navigation metadata, not an archived copy of superseded prose. Preserve searchable supporting references without counting them as primary outcomes.

Validate both directions: case to mechanism to feature, and feature to affected cases. Required dependencies may block the selected implementation; optional dependencies change its available context; conditional dependencies apply only to the declared profile. These modeled relationships do not constitute live account-readiness evidence.

## Diagrams

Provide named resources, directional relationships, a caption, accessible title and description, and linked source sections. Distinguish logical models from undisclosed implementation. Do not draw a shared runtime, memory store, or permission model without evidence.

## Product claims

Link material product behavior to official documentation. Separate native behavior, configured integrations, team-composed procedures, and synthetic evidence. Availability applies to the specific feature. Memory retrieval is not automatically model training; retention is not automatically backup and recovery.

## Presentations

Maintain HTML decks with visible chapter membership, substantive diagrams or comparisons, source-linked notes, and explicit exercise budgets. Choose content form according to the subject; no arbitrary required number of rows, cards, or procedure steps defines quality.

## Verification

Check source mapping and content consistency separately from HTML behavior. Check actual rendering, navigation, filters, figure accessibility, slide timing, and print restoration. Report what was tested and what was not. No live-service result may be inferred from a document build.

## Product resource model

Use ownership labels and colors consistently: DOC blue for this collection, AWS green for documented product concepts, EXT orange for external systems and engineering artifacts. Always state entity kind: resource, configuration member, execution record, retained state or derived view. A green label does not imply independent CRUD operations. Qualify relationship multiplicity; unknown remains unknown. Product namespace is part of identity. Keep configuration, execution, original evidence and acceptance distinct. The resource register binds features to objects without replacing or rewriting approved use cases.


## Mechanism explanations

Describe the documented process in the capability section that owns it. A mechanism explanation follows its relevant inputs, selection or execution behavior, state changes, and controls. Do not impose a fixed number of steps or render every registry row as an AWS mechanism. Link use-case steps to the corresponding authored explanation. Preserve the frozen registry for traceability, not as a second source of guide prose.


## Technical language and evidence status

Use the product object, operation, input, output, and condition as the subject of each explanation. Replace unmeasured benefit claims with documented behavior. Avoid slogans, rhetorical questions, evaluative adjectives, conversational asides, and repeated statements about the quality of the document. Retain exact AWS feature names even where their wording differs from house style.

Separate product prerequisites from team procedures. A recommended approval is not a native service gate; a proposed acceptance test is not a recorded result. Describe cancellation, deletion, publication, and permission effects for the specific object. Use one reading-conventions paragraph per guide; retain mechanism-specific constraints next to the operation.

Do not declare one retrieved documentation version newer solely because it was indexed more recently. Record conflicting content and qualify the affected procedure. Targeted rechecks do not update the review date of all retained claims. An editorial checker detects selected regressions; it does not establish technical completeness or writing quality.

## Reader hierarchy

Primary navigation follows reader tasks: Guides, Use cases, Resource model, Presentations. Each guide has one chapter hierarchy and one search. Each approved use case has one contextual page containing the unchanged narrative, workflow, configuration and verification. Mechanisms and features link to their product-guide explanations. Internal schema types and migration mappings are not primary reader destinations. Protect all six catalog JSON registers byte-for-byte.

## Capability exposition

The approved entity model is a semantic reference, not a chapter template. Organize platform explanation by the exposed configuration dimensions: scope, definition, context, invocation, integration, connectivity, execution, managed functions, interfaces/outputs, and administration. A feature names a concrete product facility; a mechanism explains its operation. Do not render every dependency-register row as an equivalent mechanism or feature. Implementation recipes remain team-authored setup instructions within use cases; distinguish them from native test-profile resources.

Guide prose is authored in Markdown. Frozen registry records provide relationships and compatibility identifiers, not automatic chapter prose. The supplied DevOps outline is the editorial basis; other product guides use only their documented facilities rather than inheriting DevOps resource types.
