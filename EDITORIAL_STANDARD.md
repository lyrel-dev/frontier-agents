# Editorial and technical acceptance standard

The unit of documentation is the product resource or mechanism, not an arbitrary fixed number of steps.

A capability explains a reusable supported ability. An operation acts on a named object. A mechanism explains documented triggers, state, execution and effects. A use case applies these to a concrete problem. A broad product function may contain several capabilities.

Every procedure must state meaningful prerequisites, configuration decisions, expected confirmation and failure interpretation. Lifecycle instructions distinguish disable, cancel, soft delete, forget and permanent deletion where the product does. Steps and diagrams have as many elements as the subject requires.

Cite the official source near the product claim. Source registers identify reviewed topics and conflicts between retrieved page versions. Missing documented implementation details remain unknown. Synthetic examples identify invented inputs, supply enough evidence to support their conclusion and include a failure branch.

Use direct descriptive prose. Do not replace product explanation with repeated generic cautions or speculative benefits. Present recommendations as engineering guidance, not native features.

Automated checks establish link, schema, fixture, browser and slide-layout properties only. They cannot certify factual completeness, successful AWS setup, diagnostic correctness, security coverage or savings. Coverage maps state detailed, linked and deferred areas.

One canonical guide per platform. Globally unique section identifiers. Presentations link to those sections. No manual archive directories or committed distribution packages; Git history is the version record.
