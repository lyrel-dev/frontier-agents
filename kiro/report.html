01 / Decision brief

Repository-scoped planning, implementation, testing and review workflows.

A useful coding agent does more than generate lines of code. It turns an understood requirement into a reviewable change, with enough implementation and test evidence for another engineer to decide whether to accept it. That requires a bounded repository context, clear behavior and an environment that can run the relevant checks.

The running example adds request-ID propagation to checkout-api without changing public behavior elsewhere. It begins with repository understanding, uses specifications when the expected behavior needs agreement, and ends at a pull request. A second example schedules a tightly scoped maintenance task. Web autonomy, local hooks and cloud sandbox controls are kept separate throughout.

Recommended starting decision

Delegate a small reviewable change with a concrete regression test. Keep merge, release and production credentials outside the task.

Audience
Software engineers, technical leads and developer-platform teams
Availability
Kiro Web is preview, requires eligible paid access, and has documented Region and administrator controls. IDE, CLI and Web features are not interchangeable.

02 / Running example

Propagate request IDs through checkout-api

Illustrative scenario, not an observed customer result or an executed demonstration.

Trigger
A developer cannot correlate an incoming checkout request with its downstream calls.
Scope
Selected repository and branch; no schema change, production access or unrelated dependency upgrades.
Deliverable
A PR/MR containing the change, meaningful tests and a review explanation.
Not done

Code was generated, but the relevant tests were not run or the diff exceeds the agreed scope.

Done means

A reviewer verifies propagation and failure behavior, confirms the tests, and makes the merge decision.

03 / Use-case execution sequence

Steps, responsibility, review records and acceptance

Each step separates documented product mechanisms from proposed team steps. Responsible roles, evidence-retention records, gates and fallbacks are not native agent assurances.

01

Understand the code before choosing the mode

Related capabilities: C01 · C04 · C10

Operation and evidence context

Use an interactive session while the problem is still ambiguous. Ask for the request path, the relevant symbols and the boundaries where request IDs disappear. The repository gives the agent evidence about the implementation; it does not prove how a deployed service behaves.

Move to autonomous work only after the desired outcome and exclusions are clear. Web sessions, local IDE/CLI work and cloud-session continuation have different entry points and controls. Verify the plan, client and administrator configuration rather than assuming a feature described for one surface exists on every other surface.

Responsible role (proposed)
Developer/repository owner
Required input and scope
Repository, branch, reproduced problem and a named reviewer.
Review record to retain (proposed)
A cited code-path explanation and a bounded task statement.
Independent acceptance gate
The owner can describe the intended behavior and what must not change.
Failure / fallback
Stay interactive and investigate missing runtime evidence instead of delegating an ambiguous outcome.

02

Make the intended behavior inspectable

Related capabilities: C02 · C03 · C11 · C12

Operation and evidence context

03

Configure the environment that will execute the work

Related capabilities: C08 · C13 · C14 · C15 · C16

Operation and evidence context

The sandbox needs the dependencies and access required to run the chosen checks. Configure setup commands, permitted network access and narrowly scoped test secrets deliberately. A failed test caused by a missing dependency is not evidence that the implementation itself is wrong or right.

MCP and Powers extend the tools available to the agent. Review their credential scope and side effects. Local permissions and hooks do not automatically govern Web execution; local file-save checks and cloud recurring jobs are different mechanisms. Keep production credentials out of the coding task.

Responsible role (proposed)
Platform or repository administrator
Required input and scope
Known setup commands, test configuration, approved tools and minimal test credentials.
Review record to retain (proposed)
An executable task environment with documented access and known limitations.
Independent acceptance gate
The same meaningful checks can run under the intended execution surface.
Failure / fallback
Record the environment failure and move verification to approved CI; do not mark an unexecuted test as passed.

04

Implement within the contract and inspect the evidence

Related capabilities: C04 · C05 · C06 · C08

Operation and evidence context

A bounded autonomous task can plan the change, edit code and open a reviewable PR. When several repositories are involved, identify each affected contract and the evidence required in each repository. The issue or prompt should name the target branch and exclude unrelated refactoring.

For the example, inspect the request-header handling, downstream propagation and tests for both existing and generated IDs. Generated tests only help when their assertions exercise the requirement and their execution result is available. A screenshot or passing command is not a substitute for reviewing what was actually checked.

Responsible role (proposed)
Implementing engineer and reviewer
Required input and scope
Approved task, repository scope and runnable verification commands.
Review record to retain (proposed)
A focused diff with test source, execution results and residual limitations.
Independent acceptance gate
Every changed area can be justified by the stated outcome.
Failure / fallback
Split an oversized change into reviewable units rather than accepting a cross-repository patch on faith.

05

Treat review feedback as new constrained work

Related capabilities: C07 · C17 · C18

Operation and evidence context

The PR is the start of independent acceptance, not the end of responsibility. Check the diff, test meaningful negative cases and provide precise feedback. Supplied CI failures can guide another iteration, but a coding workflow is not automatically a connected CI-monitoring service.

Use the correct recovery mechanism for the client. Local file checkpoints and conversation rewind are not general production rollback. IaC drafts, pipeline diagnosis and runbook writing are composed uses of coding tools; validate them with the relevant provider tooling, CI job or safe rehearsal.

Responsible role (proposed)
PR reviewer
Required input and scope
PR/MR, review comments and the actual failing check where applicable.
Review record to retain (proposed)
An updated change and a documented reviewer decision.
Independent acceptance gate
The reviewer, not the agent, decides whether the change meets the contract and can merge.
Failure / fallback
Reject or revert the branch change using normal source-control practice when acceptance fails.

06

Automate only the maintenance that is already understood

Related capabilities: C09 · C19 · C20 · C21

Operation and evidence context

A recurring dependency-maintenance job should define allowed version changes, prohibited packages, required tests and the reviewer. Kiro automations can run recurring repository tasks and propose changes; the schedule does not authorize an automatic production release.

Custom agents, skills and workflows can package repeated procedures, but their surface support and rollout conditions differ. Start with one job whose result is easy to inspect. Measure accepted changes, review effort and escaped defects before expanding the task or repository scope.

Responsible role (proposed)
Maintenance workflow owner
Required input and scope
A repeatable procedure, precise schedule, repository boundary and stop owner.
Review record to retain (proposed)
A recurring reviewable change with an audit trail and test evidence.
Independent acceptance gate
Every run remains bounded, independently reviewed and easy to pause.
Failure / fallback
Disable or narrow the automation when it produces noisy, unreviewed or out-of-scope changes.

Accept the artifact; authorize the effect separately.

Illustrative work contract

Product-neutral template. It is not a native agent configuration file, a credential container or an authorization token.

task: request-id-propagation
repository: checkout-api
branch: feature/request-id-demo
allowed_effects: [read-code, edit-branch, run-test-suite, propose-pr]
constraints: [no-schema-change, no-production-access]

Authorization and evidentiary limits

A generated recommendation, PR, finding or cost report is evidence for a decision. It is not a universal approval to act in another product.

Verify current feature availability, integration permissions and target safety before using a workflow. Preserve unresolved evidence gaps and use the existing team process when a configured path is not available.

These are proposed engineering controls, not a claim of one shared AWS permission model.
