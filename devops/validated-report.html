01 / Decision brief

Incident investigation, service-status analysis and release-readiness workflows.

During an incident, the hard part is rarely opening another dashboard. It is connecting the affected service, the deployment that preceded the symptom, and the evidence that distinguishes a plausible explanation from the actual failure. DevOps Agent brings those sources into an investigation context; the engineer still decides whether the evidence justifies a mitigation.

This report follows an illustrative checkout failure after a retry-policy change. The useful result is not a fluent root-cause statement. It is a traceable investigation, a controlled next action, and a verification record. The same context can support daily health questions and prevention work. Release-readiness review and active release testing are a distinct preview path, not a capability that becomes generally available merely because production operations are GA.

Recommended starting decision

Start with one read-heavy investigation workflow. Add action paths only after the evidence and authorization boundaries have been tested.

Audience
On-call engineers, SREs, platform engineers and service owners
Availability
Production operations: GA. Release management: preview; assess each feature and Region separately.

03 / Use-case execution sequence

Steps, responsibility, review records and acceptance

Each step separates documented product mechanisms from proposed team steps. Responsible roles, evidence-retention records, gates and fallbacks are not native agent assurances.

01

Establish the operational boundary

Related capabilities: C01 · C06

Operation and evidence context

Begin with the service and the incident window, not an unrestricted instruction to fix production. An Agent Space gathers account configuration, integrations and application context. Its topology helps the investigation understand relationships; underlying IAM and integration permissions determine what can actually be accessed.

Connect a known-good deployment reference and the telemetry needed to challenge the incident hypothesis. Missing logs are an evidence gap, not a reason to grant broad write permissions. Validate one expected read and one harmless out-of-scope denial before relying on the configuration.

Responsible role (proposed)
Platform/on-call owner
Required input and scope
Service identity, environment, incident window, deployed revision, relevant telemetry and repository access.
Review record to retain (proposed)
A scope record and a short inventory of available and missing evidence.
Independent acceptance gate
The service owner can explain the access boundary and identify who can stop the work.
Failure / fallback
Keep the incident in the normal on-call process while missing evidence or permissions are repaired.

02

Investigate, then challenge the explanation

Related capabilities: C01 · C03

Operation and evidence context

An alert, ticket or on-demand question can start the operational workflow. Ask the agent to separate observations, hypotheses and missing data. For the checkout example, the deployment time, affected resources and request failures need to agree before the change becomes the leading explanation.

Use follow-up questions to test alternatives: an upstream timeout, a capacity limit, or an unrelated configuration change. A confident answer does not eliminate competing causes. The engineer compares material claims with the source systems and preserves the evidence links for the incident record.

Responsible role (proposed)
Incident investigator
Required input and scope
Incident signal and scoped operational context.
Review record to retain (proposed)
A hypothesis ledger with supporting observations, contrary evidence and unresolved gaps.
Independent acceptance gate
At least one material claim is independently checked against its source.
Failure / fallback
Record an inconclusive investigation rather than inventing a cause or waiting indefinitely.

03

Separate a recommendation from an authorized action

Related capabilities: C02

Operation and evidence context

A mitigation proposal should state the intended effect, blast radius, validation criteria and reversal plan. In the example, reducing retries may be a candidate, but a service owner must consider whether it hides errors or shifts load elsewhere. Recommendations are reviewable artifacts, not implicit permission to modify resources.

Directed actions have their own enablement, access and approval controls. Keep the action decision attached to the exact target and operation. An approval to investigate is not approval to deploy, and a broad instruction in chat is not a substitute for the configured authorization path.

Responsible role (proposed)
Incident commander or change approver
Required input and scope
Reviewed hypothesis and a specific mitigation candidate.
Review record to retain (proposed)
An action decision with owner, target, allowed effect, rollback and verification criteria.
Independent acceptance gate
The effect is authorized through the correct product and team controls.
Failure / fallback
Execute through the established runbook or change process when the agent action path is not approved.

04

Turn an incident into owned prevention work

Related capabilities: C04 · C05

Operation and evidence context

After recovery, recurring incident patterns can inform observability, resilience, infrastructure and deployment improvements. Convert a useful recommendation into a bounded engineering item rather than leaving it as an unowned report. Preserve the original incident references so the proposed fix can be evaluated against the actual failure.

Daily health summaries are configured custom-agent workflows. Specify the question, tools, skills, schedule and audience explicitly. A scheduled prompt cannot see a database or monitoring system that has not been connected, and an automated summary still needs an owner who handles missing or stale data.

Responsible role (proposed)
Service owner and SRE
Required input and scope
Validated incident record, historical incidents and a named follow-up owner.
Review record to retain (proposed)
A prioritized improvement item or configured recurring operational report.
Independent acceptance gate
The item has measurable acceptance criteria and the scheduled output has a recipient and stop owner.
Failure / fallback
Use the existing backlog and manual report until the integrations provide adequate evidence.

05

Review the next release without confusing the test paths

Related capabilities: C07 · C08

Operation and evidence context

The follow-up retry-policy change can be reviewed for release risk. Readiness review evaluates a code change and its dependencies, policies and access implications; managed verification can add build or test evidence. These are release-preview features and should be piloted separately from the production investigation baseline.

Active release testing instead interacts with a running application. Browser or API requests can create, update or delete data and trigger business effects. Use a disposable staging target, test identities and disabled external side effects. Infrastructure write access being disabled does not make application testing read-only.

Responsible role (proposed)
Release owner
Required input and scope
Candidate revision, application context, and an authorized staging target where active testing is used.
Review record to retain (proposed)
Release findings, reproduction details and explicit residual risks.
Independent acceptance gate
The release owner checks both feature availability and the actual effects allowed against the test target.
Failure / fallback
Use prepared results or the ordinary test suite rather than testing a production endpoint to keep a demo moving.

06

Hand off code work and close on independent evidence

Related capabilities: C06 · C09 · C10 · C11 · C12 · C13 · C14 · C15 · C16 · C17 · C18 · C19

Operation and evidence context

An investigation can hand a bounded implementation task to a coding workflow. Kiro can help with code understanding, changes and tests; Amazon Q Developer has separate AWS guidance, review and transformation capabilities. Those companion tools are retained in the inventory, but they are not renamed as native DevOps Agent features.

Close the loop with a reviewed change, the normal delivery process and an independent check of the original service symptom. IaC drafts, build-log diagnoses and runbooks remain team-composed uses of coding tools. Measure accepted investigations and completed follow-ups, not the number of agent responses.

Development reviewer and SRE
Required input and scope
Evidence-linked issue with affected repository, constraints, test expectations and reviewer.
Review record to retain (proposed)
Reviewed code or operational change plus a recovery or regression-test record.
Independent acceptance gate
A human reviewer accepts the result; deployment authority and access remain local to their own systems.
Failure / fallback
Keep a failed or inconclusive change visible as unfinished work rather than closing the incident on generated text.

05 / Controls and handoff

Accept the artifact; authorize the effect separately.

Use Kiro for the code change, the Security report for an authorized application assessment, and the architecture report for the handoff contract.

Illustrative work contract

Product-neutral template. It is not a native agent configuration file, a credential container or an authorization token.

work_item: INC-DEMO-001
service: checkout-api
environment: staging
revision: DEMO-A
evidence: [incident-window, telemetry-links, deployed-diff]
allowed_effects: [read-evidence, propose-code-change]
prohibited_effects: [production-deployment]
owner: service-owner
done: reviewed-change-and-independent-verification

Authorization and evidentiary limits

A generated recommendation, PR, finding or cost report is evidence for a decision. It is not a universal approval to act in another product.

Verify current feature availability, integration permissions and target safety before using a workflow. Preserve unresolved evidence gaps and use the existing team process when a configured path is not available.

These are proposed engineering controls, not a claim of one shared AWS permission model.

Mechanisms / setup and verification extension

How this platform uses context and executes work

A recurring alarm does not prove that its previous root cause has returned. Use historical context to select hypotheses, then test those hypotheses against current telemetry. The documentation describes retained Markdown knowledge, routing by descriptions, and a managed learning process. It does not document a customer-operated model-training switch.

Historical investigations → managed learning runs → versioned memory → relevance-based retrieval → a new investigation. User instructions, selected skills and tool permissions remain separate controls.
