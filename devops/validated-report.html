Structured presentation transcript

Eight sections, with source-linked speaking notes.

Product assertions are supported below. Demonstrations are proposed, not executed. Recommendations are deliberately separated from vendor promises.

01
Presentation section

Choose by engineering task

On-screen message
Production operations, coding assistance, and AWS guidance are different jobs.

Speaker transcript

Start with the task rather than treating every AWS-branded assistant as interchangeable. DevOps Agent supports production investigation and prevention. Its release-management features are preview. Kiro supports coding workflows, while Amazon Q Developer remains relevant to AWS guidance and existing integrations. The IDE-plugin support deadline is specifically 30 April 2027; it is not a retirement notice for the whole service. Our adoption recommendation is to evaluate Kiro for new coding pilots while checking the actual editor and feature requirements.

Product evidence: [S01] [S16] [S23] [S31] [S32]

Proposed demonstration — not executed: Show the product and evidence filters. Explain that a workflow example is useful, but is not a separately documented product feature.

02
Presentation section

Make one small, reviewable code change

On-screen message
Comprehension → bounded change → tests → human review.

Speaker transcript

Use the development assistant to explain the relevant code, then ask for a small change with explicit acceptance criteria. Kiro supports chat-based changes and structured feature or bugfix specifications. Test generation is documented, but generated assertions are still code that needs review. Our proposed demonstration is a request-ID propagation fix with a narrow diff. Success means the desired behavior is reproduced and verified—not merely that the agent reports completion.

Product evidence: [S16] [S17] [S18] [S19]

Proposed demonstration — not executed: Walk through the prompt, relevant files, proposed diff, new tests, and actual CI result. Label an unexecuted demonstration as proposed.

03
Presentation section

Keep CI assistance distinct from release preview

On-screen message
Supplied-log triage is not an automatic CI connector.

Speaker transcript

The first-pass CI workflow is to provide a failed build log, identify a plausible causal error, and validate a minimal fix in the original pipeline. That is an application of coding tools, not a claim that Kiro is already watching every build. DevOps Agent has separate preview readiness reviews and managed verification testing. Exploratory release testing targets a deployed application and may change its data. Use a dedicated test environment and do not collapse these different verification modes into one feature.

Product evidence: [S20] [S10] [S11] [S12]

Proposed demonstration — not executed: Compare a supplied-log example with the two documented preview testing paths. Identify the target environment before any execution.

04
Presentation section

Investigate before authorizing remediation

On-screen message
Evidence → hypothesis → mitigation proposal → controlled action.

Speaker transcript

Begin with the affected service and a precise time window. DevOps Agent can correlate connected operational signals and expose investigation evidence. Ask the operator to distinguish observations from hypotheses and test the proposed explanation. A mitigation recommendation does not automatically authorize a production change. The documented directed-action path is disabled by default and requires explicit setup and approval. The pilot should begin with investigation and recommendation review before considering resource-changing access.

Product evidence: [S02] [S03] [S13]

Proposed demonstration — not executed: Show an investigation timeline and a mitigation proposal. Review affected resources and recovery checks; do not run a production change for the demonstration.

05
Presentation section

Turn reliability findings into owned work

On-screen message
Prevention recommendations and scheduled reports need different setup.

Speaker transcript

Recurring incident analysis produces recommendations; a scheduled health report is a configured custom-agent workflow. Give either output an owner and a verification criterion. For infrastructure work, use Kiro’s drafting and explanation capabilities without presenting them as a guaranteed Terraform, CDK, and CloudFormation validator. A source-code diff does not by itself establish live production impact. Our proposed operating loop is to review the change with the real infrastructure tooling, deploy through existing controls, and compare the result with operational evidence.

Product evidence: [S04] [S06] [S20] [S21]

Proposed demonstration — not executed: Show one prevention item and its acceptance criteria, then an IaC diff alongside the framework’s own validation output.

06
Presentation section

Treat findings as inputs, not certification

On-screen message
Keep independent security checks and explicit access controls.

Speaker transcript

Amazon Q Developer code reviews have supported-language, scope, and quota boundaries. A clean review is therefore not a statement that the entire system is secure. Likewise, an AWS explanation should not be described as account-specific analysis unless the relevant access and evidence are present. Retain independent scanners, peer review, least-privilege configuration, and a check of each product’s data handling. For existing Q IDE users, include the plugin support deadline in the transition plan.

Product evidence: [S24] [S33] [S34] [S35] [S36] [S31]

Proposed demonstration — not executed: Inspect a finding, the files actually covered, and an independently reproduced result. Review tool permissions before any agent-run command.

07
Presentation section

Make the handover evidence-linked

On-screen message
A useful output states what happened, what is known, and who acts next.

Speaker transcript

Operational chat can produce reports and investigation summaries. Our handover template adds the incident window, affected service, evidence links, unresolved questions, mitigation status, and action owners. This template is a team recommendation, not a claim of universal ticket automation. GitHub review and issue-to-PR capabilities are documented but remain preview.
